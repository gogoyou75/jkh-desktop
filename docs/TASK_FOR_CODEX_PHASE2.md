# TASK FOR CODEX — PHASE 2
## Тема: исправить sync-read для user и убрать dual-write по тарифам/ставкам

### Контекст
В предыдущем проходе уже сделано:
- write-защита owner-level ключей тарифов и ставок на backend
- owner определяется только сервером из сессии
- user не может менять тарифы и ставки через API
- добавлен endpoint сообщения об ошибке ставки
- введены owner-cache ключи:
  - `tariffs_{owner}`
  - `ref_rates_{owner}`

Но остались две критические проблемы:

1. **sync/read для non-admin сейчас реализован неверно**  
   user не должен писать тарифы и ставки, но **должен иметь право читать их с сервера**, иначе второе устройство owner не получает актуальные тарифы/ставки.

2. **сохраняется dual-write / dual-source модель**  
   одновременно живут новые owner-bound ключи и legacy ключи. Это риск рассинхрона:
   - UI может читать одно
   - расчёт может читать другое
   - sync может переносить третье

---

## ЦЕЛЬ PHASE 2

Нужно довести архитектуру до канона:

### A. READ / WRITE права
Для тарифов и ставок должно быть так:

- **READ**:
  - admin: разрешено
  - user: разрешено

- **WRITE / DELETE**:
  - admin: разрешено
  - user: запрещено (`403`)

То есть user должен иметь возможность:
- загрузить с сервера тарифы
- загрузить с сервера ставки
- видеть их на втором устройстве
- использовать их в расчётах / UI read-only

Но user не должен иметь возможность:
- сохранить тариф
- изменить тариф
- удалить тариф
- сохранить ставку
- изменить ставку
- удалить ставку

---

## B. Убрать dual-write / legacy модель
Нужно привести систему к **одному каноническому пути хранения**:

### Канонические ключи:
- `tariffs_{owner}`
- `ref_rates_{owner}`

### Требуется:
1. Найти все места, где тарифы и ставки:
   - пишутся в legacy ключи
   - читаются из legacy ключей
   - синхронизируются через legacy ключи
   - fallback'аются на legacy без необходимости

2. Убрать dual-write:
   - не писать одновременно в новые и старые ключи

3. Оставить один источник истины:
   - только owner-bound ключи

4. Если нужна миграция:
   - сделать **одноразовую миграцию чтения**
   - при наличии только legacy данных аккуратно перенести их в:
     - `tariffs_{owner}`
     - `ref_rates_{owner}`
   - после миграции работать только с новыми ключами

### Важно:
Нельзя оставлять постоянную схему:
- запись в новый ключ
- запись в старый ключ
- чтение то из одного, то из другого

Это надо убрать.

## ОБЯЗАТЕЛЬНЫЕ СЦЕНАРИИ ПРОВЕРКИ

### Сценарий 1 — admin write
- admin меняет тариф
- admin меняет ставку
- сохраняет на сервер
- всё сохраняется

### Сценарий 2 — user read
- user на другом устройстве делает загрузку с сервера
- получает актуальные тарифы
- получает актуальные ставки
- UI остаётся read-only

### Сценарий 3 — user write forbidden
- user пытается отправить write запрос на тариф
- получает `403`
- user пытается отправить write запрос на ставку
- получает `403`

### Сценарий 4 — canonical only
- после миграции данные читаются из:
  - `tariffs_{owner}`
  - `ref_rates_{owner}`
- нет постоянной записи в legacy ключи

### Сценарий 5 — no desync
- устройство 1: admin меняет тариф/ставку
- устройство 2: user того же owner делает load/sync
- значения совпадают
