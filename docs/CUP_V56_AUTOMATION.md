# ЦУП v5.6 — автоматизация управления схемой

## Границы версии

v5.6 — отдельный `scripts/jkh_server_menu_v5_6.sh`; проверенный v5.5 сохранён без изменений. Пункты 0–18 и 19.1–19.8 остаются доступны. Новый 19.9 оркестрирует существующие Schema Control, Alembic, Maintenance и Restore. `schema_control.py`, `maintenance_control.py`, бизнес-код, schema_contract, frozen snapshot и опубликованные ревизии не переписываются.

Архитектура независимых БД и ролей описана в [контракте v5.5](CUP_V55_SCHEMA_MANAGEMENT.md). Текущая схема остаётся cup_5502; номер версии меню не создаёт новую ревизию приложения. Подтверждённые владельцем результаты v5.5 на VPS LAB не заменяют отдельное испытание v5.6.

## Запуск одной командой

Windows, рабочая папка репозитория:

```powershell
.\scripts\cup.cmd LOCAL_LAB
```

Git Bash / Linux, рабочая папка репозитория:

```bash
bash scripts/cup.sh LOCAL_LAB
```

Профили: LOCAL_LAB, VPS_LAB, PROD. Launcher использует уже установленные Git Bash и Python 3.11+; ничего не устанавливает и не меняет execution policy, системные настройки, DACL или реальные учётные записи. Переменные credentials не нужно вручную экспортировать. На Windows используется cmd-wrapper, а не ps1 с обходом execution policy.

Однократно разместите **несекретный** launch.json в `<папка_репозитория>/.schema-state/<LOCAL_LAB|LAB|PROD>/launch.json`. Можно явно выбрать другой приватный файл через CUP_V56_CONFIG. В нём только пути и идентификаторы среды, без passwords/tokens. Пример структуры (пути заменить существующими):

```json
{
  "format": 1,
  "profile": "LOCAL_LAB",
  "project_dir": "C:/DEV/CONTROL_CENTER/jkh-cup-v54-release-20261124",
  "db_env_file": "C:/private-cup/local-db.env",
  "admin_env_file": "C:/private-cup/local-maintenance-restore.env",
  "compose_files": ["C:/DEV/CONTROL_CENTER/jkh-cup-v54-release-20261124/docker-compose.local.yml"],
  "mysql_container": "jkh_local_mysql",
  "site_check": "http://127.0.0.1:18080"
}
```

Compose-файлы должны быть существующими и принадлежащими выбранному проекту; пример не создаёт инфраструктуру и не гарантирует соответствие конкретной LOCAL-конфигурации. Используйте уже проверенные локальные имена/порты/политику. Для VPS_LAB project_dir должен быть /root/jkh-lab, для PROD — /root/jkh. Автоматического перехода к другой БД/среде нет. Пункт 12 запускает launcher выбранного профиля заново, чтобы не переносить административную конфигурацию предыдущей среды.

Файл db_env_file — существующий доверенный Bash environment-файл с ENV_TYPE и пятью DB_* полями. admin_env_file — существующий файл шести MAINT_* и шести RESTORE_* полей. ENV_TYPE для VPS_LAB — LAB; для LOCAL — LOCAL_LAB; для PROD — PROD. RESTORE использует исключительно выделенную пустую cup_restore_* БД с LOCAL_LAB-профилем; для серверных сред сохраняется проверка отдельного MySQL server_uuid. MIGRATION_* не требуется: учётной записью управляет Maintenance.

Существующий policy.json и его каталог состояния также должны быть приватными; это проверяется и при внешнем CUP_V56_CONFIG. Файлы credentials доверенные и могут исполняться Bash source только внутри короткоживущего tool-процесса. Они не добавляются в Git, образ, argv или environment постоянно работающего API. Небезопасные group/world permissions, symlink и неверные profiles блокируются. Linux: владелец — текущий пользователь, files 0600, закрытый каталог без чужой записи. Windows: проверяются владелец и DACL файла и родителя; доступ разрешён текущему владельцу, SYSTEM и Administrators. CREATOR OWNER допускается только при проверенном владельце. Проверка читает DACL через .NET без загрузки PowerShell Security-модуля и без изменения политики. При избыточных разрешениях launcher блокирует работу; самостоятельно разрешения не ослабляет и не переписывает. Синтетическая Windows temp-фикстура с чужим FullControl была корректно заблокирована.

Отсутствие конфигурации возвращает RESULT: BLOCKED с инструкцией и не вызывает Docker/БД. Для фактического использования владелец должен подготовить приватную конфигурацию, существующие credentials и maintenance policy. Настройка ролей v5.5 не выполняется повторно.

## Новый интерфейс

```text
19.9 — Автоматическое обновление структуры БД
Среда: LOCAL_LAB; целевая ревизия: cup_5502
Необходимые изменения: создание bulk_calc_verify_jobs, bulk_calc_verify_job_items
Подтвердите показанный план: APPROVE LOCAL_LAB
Этап: backup и испытательное восстановление — выполнен
Этап: миграция и проверка — выполнен
RESULT: SUCCESS
Среда: LOCAL_LAB
Выполнено: план согласован; схема и данные проверены; записи и сервисы возобновлены
Не выполнено: перенос данных между средами
Приложение: HEALTHY | БД: VERIFIED_WRITES_RESUMED
Далее: продолжить работу
```

plan_id/backup_id больше не требуется искать или вводить. Полный plan_id передаётся программой как привязка к показанному плану, а владелец подтверждает выбранный профиль. PROD дополнительно сохраняет YES_PROD. При истёкшем/изменённом плане действие блокируется: повторный 19.9 показывает актуальный план и требует новое подтверждение. Старое подтверждение не переносится.

19.1–19.8 остаются диагностическими/восстановительными точками. 19.4 сохраняет план; 19.5 согласует его, блокирует writers и создаёт проверенный backup; 19.6 находит связанный план/backup автоматически; 19.7 проверяет сохранность данных и схему перед возобновлением, затем проверяет API. 19.8 позволяет просмотреть очищенные JSON/логи и journal. Возврат после одной операции ведёт в основное меню.

## Документы, подтверждение и целостность

`backend/schema_workflow.py` — только координатор проверенных Controller-операций, не второй движок миграций. Документы в `<state>/workflow/{plans,backups}` содержат профиль, payload и SHA256. active.json атомарно связывает выбранную операцию, plan_id, database_id, owner approval, backup_id, исходные data-baselines и фазу. Документы привязаны к версии workflow-кода; подмена и неподдерживаемое продолжение после смены реализации блокируются. Приватный каталог — доверенная граница: обладатель прав владельца/администратора хоста вне модели защиты, это не электронная подпись против администратора.

Проверяются digest плана, contract_id, migration_id, target revision, database identity (server_uuid/DB/profile), schema fingerprint, 15-минутный срок, факт restore и hash файла backup. Документ wrapper должен совпадать с исходным core receipt. При отсутствии active допускается только единственный однозначно подходящий сохранённый план; несколько вариантов блокируются. Backup выбирается по явной привязке операции либо единственному точному совпадению, а не по времени/имени «последнего». Несоответствие или неоднозначность блокирует миграцию.

Смена плана требует нового подтверждения. При истечении срока уже проверенный **явно связанный** backup может использоваться вновь только при совпадении DB/fingerprint/целостности и сохранности исходных данных под Maintenance. После частичного DDL нужен свежий план и новый проверенный backup в новой пустой restore-БД. Занятый restore-target никогда не очищается автоматически.

## Последовательность 19.9

Проверка среды/Compose/writers → план и показ изменений → owner approval → остановка исходно работающих writer-сервисов → durable fence → backup/restore → повторная проверка согласованного плана → Controller.apply точной ревизии Alembic → проверка фактической схемы и исходных данных → Controller.maintenance_resume → запуск только исходно работающих сервисов → проверка HTTP и backend-кода → итог.

При action=noop и отсутствии активного fence приложение не останавливается, backup не создаётся, DDL не запускается. Схема и приложение всё равно проверяются. Ручной no-op 19.6/19.7 также не требует искусственного maintenance.

Опубликованные Alembic-ревизии, разделение ролей, проверки неизвестных writers и финансовой совместимости не изменяются. Служебный инструмент получает существующие scoped DB/MAINT/RESTORE, постоянный API не получает административных групп. Bash не выполняет SQL-миграции.

## Сбои и безопасное продолжение

Любая ошибка останавливает последующие этапы и не превращается в SUCCESS. Во время backup/migration/verify persistent writer locks остаются; shell cleanup освобождает только собственный lock ЦУП. SIGKILL, потеря соединения и неявный MySQL DDL COMMIT не приводят к автоматическому downgrade или снятию fence.

Фаза MIGRATING записывается **до** Controller.apply. После потерянного ответа на уже выполненный COMMIT новая диагностика может показать noop; это не разрешение забыть старый backup. Сначала проверяются все сохранённые baselines исходных данных. Только после этого формируется новое предложение и требуется подтверждение. Повреждённые финансовые данные нельзя «узаконить» новым backup или noop-планом.

Если схема/данные проверены и доступ уже возвращён, но запуск API/HTTP/version check не подтверждён, итог FAILED. БД не откатывается. Состояние RESUMED позволяет повторить 19.7 или 19.9 для проверки/старта первоначально работавших сервисов. Уже разрешённые последующие пользовательские записи не сравниваются с допусковым старым backup как с неизменной БД.

Если Maintenance уже активен, но v5.6 operation-documents отсутствуют, новый baseline не создаётся и записи не открываются: завершите проверенный recovery исходной v5.5 или отдельно согласуйте восстановление документов. Уже работающую актуальную БД без pending-операции 19.7 только проверяет, не создавая искусственный maintenance. Потеря state/policy, недостоверный документ или неизвестная схема — BLOCKED с безопасной рекомендацией. Не удаляйте state, не снимайте account locks вручную и не выполняйте stamp ради продолжения. После смены самой версии workflow старые execution-documents требуют отдельного проверенного recovery, а не молчаливого переноса approvals.

## Образ и вывод

При неизменном коде инструмент готовится один раз на операцию/автоцикл. Проверяются исходный fingerprint до/после build, отсутствие credentials/state в build context, SHA256 image ID, backend app.py, requirements и установленные pinned dependencies. One-off Compose run закрепляется на image ID и pull=never; повторных --build внутри цикла нет. Изменение кода или pin-документа останавливает автоматический цикл. Перед итоговым успехом проверяются backend-файл работающего API и HTTP site/API auth; один SELECT 1 или HTTP не является проверкой схемы.

В обычном режиме выводятся шаги и единый RESULT: SUCCESS/FAILED/BLOCKED, среда, выполненные/невыполненные действия, подтверждённые состояния приложения/БД, причина и следующий шаг. Диагностические пункты не объявляют непроверенное приложение здоровым. Технические результаты доступны в `.schema-state/<env>/logs` через 19.8. Секреты очищаются **в потоке до записи**, без файлов сырых логов; JSON остаётся валидным. Из argv/журналов исключены значения credentials. Приватные backups содержат данные по назначению и не являются техническими журналами.

## Будущий пункт 20 — только требования

Копирование содержимого — отдельная владелец-инициируемая операция, не часть обновления структуры. Возможные направления: PROD → VPS LAB, VPS LAB → LOCAL LAB, при необходимости PROD → LOCAL LAB. Нужны backup принимающей БД, проверка направления/идентичностей, явное подтверждение, защита/анонимизация персональных данных и проверка совместимости после восстановления. Перезапись PROD экспериментальными данными запрещена. Реализация и пункт меню 20 в этом этапе отсутствуют. Isolated restore для валидации backup не является механизмом переноса рабочих БД.


Workflow-набор включает прежние v5.5/Maintenance/No Name регрессии и новые сценарии. Bash использует изолированные UI/Docker-фикстуры; реальная версия tool-образа дополнительно проверяется read-only контейнером с network=none. Границы доказательств: Windows launcher проверен в сценарии отсутствующей конфигурации и DACL rejection; рабочий приватный launch-профиль должен предоставить владелец. Для v5.6 нужен следующий отдельно согласованный этап VPS LAB; прежний успешный VPS LAB v5.5 не означает испытание нового UI.
