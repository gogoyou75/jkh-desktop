## 0. Область действия

Документ фиксирует:
- предметную логику карточки абонента;
- границы owner-данных;
- правила тарифов и ставок;
- ограничения по ролям;
- базовые требования к синхронизации.

Если есть противоречие со старыми формулировками, применять актуальные правила из этого документа и из `LOGIC_SPEC.md`.

---

## 1. Источник истины (CRITICAL)

**Карточка абонента** остаётся источником истины для финансовой логики абонента.  
Но для многопользовательской архитектуры дополнительно фиксируется:

- серверная база / серверное owner-хранилище — источник истины для синхронизации;
- localStorage — рабочая копия и кэш.

То есть:
- расчётная логика абонента исходит из карточки и ledger;
- архитектурная истина хранения и прав доступа исходит с сервера.

---

## 2. payments_<LS> — единый помесячный ledger (CRITICAL)

`payments_<LS>` — единая таблица-реестр по месяцам.

Инварианты:
- в месяце допускается строка начисления и одна или несколько строк оплат;
- начисление не должно ретроактивно переписываться;
- оплата за период влияет только на пеню;
- агрегация месяца остаётся канонической:
  - `accruedYM = max(accrued)`
  - `paidYM = sum(paid)`
  - `debtYM = max(0, accruedYM - paidYM)`

---

## 3. Оплата за период (CRITICAL)

`use_period / pay_for_period / period_from / period_to`:
- влияет только на расчёт пени;
- не меняет основной долг;
- не меняет фактическую дату оплаты;
- не переписывает прошлые месяцы.

---

## 4. Исключённые периоды (CRITICAL)

Исключённые периоды:
- отключают только пеню;
- не меняют основной долг;
- должны корректно учитываться при расчёте на сервере и на клиенте.

Если период исключён, а пеня продолжает считаться — это BUG.

---

## 5. Тарифы (UPDATED)

### 5.1. Уровень хранения
Тарифы принадлежат owner, а не конкретному абоненту.

### 5.2. Принцип
- у каждого пользователя своя база тарифов;
- все его абоненты используют этот owner-набор тарифов;
- тариф не должен размножаться по абонентам как отдельная база.

### 5.3. Права
- admin: может изменять;
- user: только просмотр.

---

## 6. Ставка рефинансирования (UPDATED)

### 6.1. Уровень хранения
Ставки рефинансирования принадлежат owner и применяются ко всем его абонентам.

### 6.2. Права
- изменять ставки может только admin;
- user не имеет права редактирования;
- UI user-режима только информационный.

### 6.3. Будущее развитие
В дальнейшем допускается серверное автообновление ставок из интернета, но:
- только через backend;
- только с логированием;
- только с сохранением истории;
- желательно с подтверждением или откатом администратором.

---

## 7. Справка для суда (CRITICAL)

- месячные колонки считаются строго за месяц;
- итог на дату обязан совпадать с карточкой абонента;
- изменение правил справки не должно ломать ledger.

---

## 8. ES-modules для старой file:// логики

Ограничение версии v1.5.x про отсутствие обязательной модульной сборки сохраняется для офлайн-воспроизводимости там, где это ещё актуально.

---

## 9. Изоляция owner (CRITICAL)

- owner определяется только сервером;
- owner нельзя брать из frontend как истину;
- save/load/delete/sync выполняются только в owner-контексте сессии.

Нарушение этого правила — критическая ошибка безопасности.

---

## 10. Синхронизация (CRITICAL)

Требование:
- тарифы и ставки одного owner должны быть одинаковыми на всех его устройствах после server sync.

Если на одном компьютере тариф изменился, а на другом после загрузки с сервера не изменился — это критический баг.

---

## 11. Правило фиксации

Любая правка owner-логики, тарифов, ставок, синхронизации или ролей:
- обновляет `CRITICAL_CHANGELOG.md`;
- обновляет чек-листы;
- сопровождается регрессионной проверкой.
