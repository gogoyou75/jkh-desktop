## 1. Базовая архитектура

### 1.1. Server-first

Серверная БД является главным источником данных.

Frontend/localStorage/JKHStore — это рабочий кэш и транспортный слой. UI может читать локальный owner-scoped cache после server-first загрузки, но не должен считать localStorage главным источником истины.

Правильная цепочка:

```text
login/session
→ server-first load
→ owner-scoped local cache
→ render UI
→ точечное сохранение / sync
```

Запрещено:

- строить важные страницы до готовности данных;
- писать данные без owner-контекста;
- считать `DOMContentLoaded` достаточным событием готовности;
- молча создавать пустые ledger/ключи до загрузки server-first данных.

## 2. Owner, роли и доступ

### 2.1. Owner

Все рабочие данные принадлежат конкретному `owner`.

К owner-bound данным относятся:

- `abonents_db_v1`
- `payments_<uid>`
- `tariffs_<owner>`
- `organization_requisites_v1`
- `organization_signers_v1`
- `payment_sources_v1`
- `exclude_periods_*`
- `calc_period_*`
- `report_period_*`
- `moratorium_*`
- notes/service UI keys, если они относятся к базе пользователя.

### 2.2. GLOBAL данные

GLOBAL/admin-only данные:

```text
refinancing_rates_normal_v1
refinancing_rates_moratorium_v1
```

Они общие для системы, читаются всеми ролями, но изменяются только администратором.

### 2.3. Роли

- `admin` — может редактировать глобальные ставки и выполнять админ-операции.
- владелец базы / active owner — может редактировать свои owner-bound данные, если это разрешено сценарием.
- `user` — не должен редактировать чужие данные и GLOBAL-справочники.
- `guest` и `ALL` — только чтение.

## 3. Storage / Data Access

### 3.1. JKHStore как обязательная граница

Все операции чтения/записи runtime-хранилища должны идти через `JKHStore` / `JKHPersist` / утверждённые API-обёртки.

Прямое использование `localStorage` для рабочих данных запрещено, кроме явно разрешённых внутренних механизмов совместимости/миграции.

### 3.2. Scoped key

Runtime-ключи изолируются по owner. Внутренний формат scope может выглядеть как:

```text
jkhdb::<owner>::<key>
```

Базовая логика не должна смешивать ключи разных owner.

### 3.3. Upload whitelist

Upload должен работать по whitelist, а не по blacklist.

Разрешён принцип:

```text
отправлять только явно разрешённые ключи
```

Запрещён принцип:

```text
отправлять всё, кроме нескольких запрещённых ключей
```

## 4. UID-only payments canon

### 4.1. Главный ключ оплат

Лицевой счёт (`ЛС`, `abonentId`, `account_number`) больше не является техническим ключом оплат.

Единственный технический ключ ledger:

```text
payments_<uid>
```

Запрещено для актуальной логики:

```text
payments_<ЛС>
payments_<abonentId>
payments_<accountNumber>
payments_<ls>
```

### 4.2. Резолвер

Все модули должны получать ключ оплат через канонический резолвер:

```js
window.getPaymentsKeyForAbonent(abonentId)
```

Если ключ не получен — операция блокируется. Нельзя делать fallback на `payments_<ЛС>`.

### 4.3. UID обязателен

У каждого абонента должен быть `uid`.

При создании абонента:

- `uid` генерируется всегда;
- повторение ЛС допустимо;
- повторение UID запрещено;
- новый абонент не наследует старый ledger по ЛС.

## 5. Ledger / Payment Engine

### 5.1. Ledger — не журнал событий

`payments_<uid>` — это помесячный ledger абонента.

Он может содержать в одном месяце:

- строку начисления;
- одну или несколько строк оплат;
- строки с ручным указанием “оплата за период”.

Ledger не является чистым журналом событий. Это рабочая таблица для расчётов.

### 5.2. Одно начисление на месяц

В одном месяце должно быть только одно начисление.

Если строк за месяц несколько:

- начисление хранится только в строке с минимальным `id`;
- остальные строки месяца должны иметь `accrued = 0`.

### 5.3. Автосоздание строки начисления

Если за месяц ответственности нет строки ledger, autoaccrual может создать строку начисления.

Это финансово критическое действие, потому что система создаёт долг. Оно должно быть описано, логироваться и не должно происходить до готовности данных и UID-ключа.

### 5.4. Data contract строки платежа

Строка ledger должна приводиться к контракту:

```js
{
  id: number,
  year: "YYYY",
  month: "01".."12",
  accrued: number,
  paid: number >= 0,
  paid_date: "YYYY-MM-DD" или "",
  source: string,
  use_period: boolean,
  period_from_m: "01".."12",
  period_from_y: "YYYY",
  period_to_m: "01".."12",
  period_to_y: "YYYY",
  pay_main: number,
  pay_penalty: number,
  total_debt: number
}
```

### 5.5. Дата оплаты

Дата оплаты должна быть календарной датой без timezone-сдвига.

ISO `YYYY-MM-DD` нельзя парсить так, чтобы браузер сдвигал её на сутки. Внутри UI и импорта дата должна нормализоваться осознанно.

### 5.6. “Оплата за период”

`use_period` / “Оплата за период” влияет только на расчёт пени и назначение периода оплаты. Оно не имеет права менять фактическую дату оплаты задним числом.

## 6. CalcEngine / юридическая модель долга и пени

### 6.1. Главный принцип

`calc_engine.js` — юридическое ядро расчётов. Изменять его можно только отдельным ТЗ.

UI, справки и импорт не должны изобретать собственную формулу долга и пени.

### 6.2. Пеня

Пеня считается ежедневно по каждому обязательству отдельно.

Правила:

- первые 30 дней просрочки: пеня = 0;
- с 31 по 90 день: применяется `1/300` ставки;
- с 91 дня: применяется `1/130` ставки;
- ставка берётся на каждый день по истории ставок;
- исключённые периоды отключают только пеню, основной долг не трогают.

### 6.3. Ограничение ставки 9.5% до 2027

Критическое юридическое правило:

```text
Если дата расчёта раньше 01.01.2027 и фактическая ставка ЦБ выше 9.5%,
для расчёта пени применяется 9.5%.
```

Фактическая ставка остаётся в справочнике как историческое значение, но effective-rate для пени ограничивается:

```text
effective_rate = min(actual_rate, 9.5%) до 01.01.2027
```

После 01.01.2027 применяется фактическая ставка без ограничения.

### 6.4. FIFO

Платежи распределяются FIFO:

```text
старые начисления закрываются раньше новых
```

Платёж закрывает самый ранний непогашенный долг.

### 6.5. Платёж без периода не уходит в будущее

Если у платежа не указан ручной период оплаты, он не должен гасить будущие месяцы за пределами допустимой логики расчётного периода.

### 6.6. Переплата

Переплата должна учитываться как аванс.

В текущей модели:

- переплата сначала уменьшает основной долг;
- затем может участвовать в уменьшении пени согласно правилам calc engine;
- отрицательный основной долг допустим как отражение аванса, если сценарий расчёта это разрешает.

### 6.7. Ставка раньше первой записи

Канон проекта:

Если дата начала расчёта/регистрации/долга раньше первой доступной ставки рефинансирования:

- показать понятное информационное предупреждение;
- остановить расчёт пени и судебной справки до исправления;
- запрещено молча применять первую найденную ставку задним числом;
- запрещено молча считать пеню как 0.

Статус: **требует проверки/исправления в коде**, потому что аудит показал риск старого поведения.

## 7. Ставки рефинансирования

### 7.1. Ключи

```text
refinancing_rates_normal_v1
refinancing_rates_moratorium_v1
```

### 7.2. Права

Изменять ставки может только `admin`.

Все остальные роли — только просмотр.

### 7.3. Структура

Ставки хранятся как история:

```js
{ from: "ДД.ММ.ГГГГ", rate: "9.50" }
```

Логическое правило:

```text
ставка действует с даты from до следующей записи
```

### 7.4. Мораторий

Если для абонента включён режим моратория, calc engine использует справочник мораторных ставок.

### 7.5. Требования к будущей доработке

Ставки должны иметь:

- строгую валидацию дат;
- запрет дублей даты;
- историю изменений;
- audit log;
- защиту от тихой подмены прошлых значений;
- понятный контроль “дыр” в периодах.

## 8. Тарифы

### 8.1. Ключ

Тарифы хранятся per owner:

```text
tariffs_<owner>
```

Legacy-ключи тарифов могут читаться только для миграции/совместимости, но не должны быть новым источником записи.

### 8.2. Модель тарифа

Актуальная модель тарифа:

```js
{
  id,
  code,
  title,
  type: "per_m2" | "fixed_month",
  active: boolean,
  rates: [
    { from: "YYYY-MM-01", value: number }
  ]
}
```

### 8.3. Типы

- `per_m2` — ставка умножается на площадь.
- `fixed_month` — фиксированная сумма за месяц.

### 8.4. Дата начала ставки

Дата начала тарифа всегда нормализуется к первому числу месяца:

```text
YYYY-MM-01
```

### 8.5. Действие ставки

Ставка действует с даты начала до следующей ставки этого тарифа.

Если ставка меняется внутри месяца, autoaccrual должен делить начисление пропорционально дням действия каждой ставки.

### 8.6. Перерасчёт

Изменение тарифа влияет на начисления всех абонентов данного owner.

После изменения тарифов должен выполняться контролируемый перерасчёт начислений.

## 9. AutoAccrual

### 9.1. Назначение

`autoaccrual_engine.js` создаёт и восстанавливает начисления в ledger `payments_<uid>`.

### 9.2. Период начисления

Начисления создаются:

```text
с даты начала ответственности / calcStartDate
до dateTo / calcEndDate / текущего месяца, если период открыт
```

### 9.3. Формула

Начисление месяца:

```text
sum(per_m2 tariffs × площадь × доля дней действия) + sum(fixed_month tariffs × доля дней действия)
```

### 9.4. Смена тарифа внутри месяца

Если ставка тарифа меняется внутри месяца, месячное начисление делится по дням.

### 9.5. Смена ответственного внутри месяца

Если ответственный меняется внутри месяца, начисление делится по дням ответственности на основании `AbonentsDB.links`.

### 9.6. Зависимость от links

`links` должны быть валидными:

- без пересечений для одной квартиры;
- с корректными `dateFrom/dateTo`;
- с привязкой к нужной квартире/regnum;
- с закрытием старого active-link перед открытием нового.

Если `links` повреждены, начисления могут быть неверными.

### 9.7. Сохранение

Если autoaccrual изменил ledger, он сохраняет результат в `payments_<uid>` в owner-scope.

Запрещено возвращать `changed:true`, если фактически строк нет или сохранить нечего.

## 10. Судебная справка

### 10.1. Назначение

`spravka_sud.js` — производный документ. Он не должен менять юридическую формулу расчёта.

### 10.2. Источник расчёта

Справка должна использовать `calc_engine.js` для расчёта итогов, долга, пени и судебной разбивки.

### 10.3. UID payments

Справка читает только `payments_<uid>`.

Если UID-ключ не определён — построение блокируется понятной ошибкой.

### 10.4. Autoaccrual внутри справки

Текущее поведение допускает запуск autoaccrual, если ledger пустой или не содержит начислений.

Это признано архитектурным риском, потому что производный документ может изменить данные.

До отдельной доработки правило такое:

- справка может попытаться восстановить начисления только если ledger непригоден;
- после пересчёта flush не должен ломать построение, если локальные данные есть;
- результат должен логироваться;
- дальнейшая цель — вынести изменение данных из справки в подготовительный/явно подтверждённый сценарий.

### 10.5. Запрет fallback 2000

Fallback-дата `2000-01-01` не должна применяться как молчаливый источник расчёта.

Если дата начала расчёта не найдена, справка должна показать ошибку и остановиться.

Статус: **требует исправления**, если в коде остался fallback.

## 12. Import XLS

### 12.1. Назначение

`import_xls.html` — точка входа данных из Excel.

Это самая рискованная зона, потому что ошибка импорта заражает всю систему.

### 12.2. Два шага

1. Первичка: идентификация/обновление абонентов, UID, площади.
2. Платежи: импорт оплат только по UID.

### 12.3. UID для платежей

Платежи импортируются только по UID.

Если UID нет — платежи не применяются.

### 12.4. Начисления не импортируются

Начисления из Excel не импортируются. Они считаются системой автоматически:

```text
тариф × площадь × период ответственности
```

### 12.5. Опасные fallback

Сейчас в импорте есть распознавание структуры Excel и fallback-логика.

Канон будущей доработки:

- должен быть строгий контракт шаблона;
- auto-detect допустим только как preview/подсказка, но не как тихое основание записи;
- дата платежа не должна додумываться молча как `01.MM.YYYY` без явной маркировки;
- конфликты платежей должны решаться сервером;
- должен быть audit log импорта;
- rollback должен быть гарантированным.

## 13. Premises / links / merge / split

### 13.1. Links

Связь ответственного и квартиры хранится в `links`.

Активный link имеет пустой `dateTo`.

При смене ответственного старый link закрывается датой `newDateFrom - 1 день`.

### 13.2. Merge

Объединение квартир:

- старые квартиры получают `status = "merged"`;
- старые links закрываются;
- старые абоненты получают `calcEndDate`;
- новая квартира получает новый regnum;
- новый абонент получает новый ЛС и новый UID;
- старые платежи/долги остаются на старых UID;
- событие пишется в `premiseEvents`.

### 13.3. Split

Разъединение квартир v1:

- не распределяет долги, оплаты, начисления и пеню автоматически;
- закрывает исходную квартиру;
- создаёт новые квартиры;
- создаёт/назначает новых ответственных;
- новые абоненты получают новые UID;
- новые ledger начинаются с новых `payments_<uid>`;
- событие пишется в `premiseEvents`.

### 14.1. TRACEABILITY_MATRIX

- `LOGIC_SPEC.md`

## 16. Минимальные регресс-проверки

После изменений проверять:

```bash
node --check web/calc_engine.js
node --check web/storage.js
node --check web/payment_table.js
node --check web/autoaccrual_engine.js
node --check web/spravka_sud.js
```

UI-проверки:

1. Логин → server-first загрузка → главная таблица не пустая.
2. Карточка абонента читает `payments_<uid>`.
3. Новый абонент с повторным ЛС не видит старые платежи.
4. Справка суда строится через calc engine.
5. Если нет ставки на раннюю дату — расчёт останавливается предупреждением.
6. Изменение тарифа пересчитывает начисления контролируемо.
7. Импорт платежей без UID невозможен.
8. Ставки рефинансирования редактирует только admin.
