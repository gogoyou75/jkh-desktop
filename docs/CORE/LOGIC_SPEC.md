## 0. Назначение документа

Этот документ фиксирует обязательную архитектуру и права доступа для:
- тарифов;
- ставок рефинансирования;
- изоляции данных по owner;
- синхронизации данных между устройствами;
- будущего автoобновления ставок с сервера.

Если старые документы противоречат этому файлу, приоритет у этого файла и у `CHANGELOG.md`.

## 1. Ownership и изоляция данных (CRITICAL)

### 1.1. Общее правило
Все рабочие данные системы принадлежат конкретному `owner` (user_id).

К сущностям owner-пространства относятся:
- abonents
- payments
- accruals
- tariffs
- refinance_rates
- exclusion_periods
- premises / links
- notes / calc periods / report periods / related service data

### 1.2. Источник owner
`owner` определяется **только сервером** из серверной сессии.

Запрещено:
- передавать owner с клиента как источник истины;
- доверять owner из localStorage, query string, body, hidden fields;
- выполнять save/load/delete/sync без серверного owner.

### 1.3. Последствие
Каждый пользователь работает только со своей базой.  
Данные разных пользователей полностью изолированы.

---

## 2. Источник истины и синхронизация

### 2.1. Источник истины
- **Backend / серверная БД** — источник истины.
- **Frontend / localStorage** — рабочий кэш, офлайн-копия и транспортный слой.

### 2.1.1. Обязательные миграции схемы БД
Любое изменение backend-моделей БД, включая добавление колонок в SQLAlchemy-модели, должно сопровождаться явной миграцией схемы БД и deploy-проверкой структуры таблиц.

Для `import_batches` после добавления audit-полей обязательна миграция:

```sql
ALTER TABLE import_batches
ADD COLUMN rows_skipped INT NOT NULL DEFAULT 0,
ADD COLUMN file_name VARCHAR(255) NULL,
ADD COLUMN uploaded_by VARCHAR(255) NULL,
ADD COLUMN error_message TEXT NULL;
```

После backend-deploy необходимо выполнить `DESCRIBE import_batches;` и сверить наличие колонок `rows_skipped`, `file_name`, `uploaded_by`, `error_message`.

### 2.2. Синхронизация
После логина и при явной загрузке с сервера клиент должен иметь возможность получить **полный набор данных owner**.

Минимальное требование:
- сервер поддерживает выгрузку полного набора ключей owner (`store_dump` или эквивалент);
- клиент умеет восстановить локальную рабочую копию из серверного набора.

### 2.3. Критический дефект
Если тарифы или ставки не синхронизируются между двумя устройствами одного owner, это считается **критической ошибкой синхронизации**.

## 3. Тарифы

### 3.1. Модель
Тарифы являются сущностью уровня `owner`.

Правильно:
- у каждого пользователя своя независимая база тарифов;
- один набор тарифов действует для всех абонентов этого пользователя;
- тарифы не принадлежат отдельному абоненту.

Неправильно:
- хранить тарифы на уровне конкретного абонента;
- дублировать один и тот же тариф по каждому абоненту;
- менять логику так, чтобы тариф был частью карточки абонента как первичный источник.

### 3.2. Структура
Тариф хранится как историческая запись:
- tariff_content
- tariff_repair
- start_date

Правило:
- последний тариф действует до появления нового;
- тариф вводится с начала месяца;
- один месяц имеет одну актуальную тарифную запись на owner-уровне.

### 3.3. Права доступа
- **Администратор**: создание / редактирование / удаление тарифов.
- **Пользователь**: только просмотр (`read-only`).

### 3.4. Применение
Начисление абонента считается по формуле:

`начисление = тарифы owner × площадь абонента`

Абонент хранит:
- площадь;
- адресные и идентификационные данные;
- свою финансовую историю.

Абонент **не хранит собственный тарифный справочник**.

---

## 4. Ставка рефинансирования

### 4.1. Модель
Ставки рефинансирования являются сущностью уровня `owner`.

Они:
- общие для всех абонентов данного пользователя;
- применяются в расчёте пени ко всем его абонентам;
- хранятся как история по датам.

### 4.2. Жёсткое правило прав доступа
**Изменять ставки рефинансирования может только администратор.**

Права:
- **Администратор**: полный CRUD.
- **Пользователь**: только просмотр (`read-only`), без права изменения.

Любая попытка изменения ставки от роли `user` должна завершаться отказом доступа.

### 4.3. Пересчёт
После изменения ставки:
- система должна инициировать корректный пересчёт пени;
- перерасчёт должен быть воспроизводимым и аудируемым;
- история прежних ставок обязана сохраняться.

### 4.4. Логирование
Каждое изменение ставки должно логироваться минимум с полями:
- user_id / actor_id
- старая ставка
- новая ставка
- дата изменения
- тип изменения
- источник изменения (manual / import / auto-update)

---

## 5. Сообщение об ошибке ставки

### 5.1. Назначение
Пользователь не меняет ставку напрямую, но может отправить сигнал:
**«ошибка в ставке рефинансирования»**.

### 5.2. Минимальная модель
Сообщение должно содержать:
- type = `refinance_rate_issue`
- text
- created_at
- user_id / owner
- optional related_date

### 5.3. Смысл
Разделение обязанностей:
- изменение справочника ставок — только администратор;
- сообщение о возможной ошибке — пользователь.

---

## 6. Будущее автообновление ставок из интернета

### 6.1. Разрешённое направление развития
В дальнейшем допускается автоматическое обновление ставок из внешнего источника:
- через API;
- через серверный парсер;
- через контролируемый AI-assisted механизм.

### 6.2. Ограничения
Такое обновление допускается **только на сервере** и только при соблюдении правил:
- сохраняется история всех значений;
- фиксируется источник данных;
- логируется время и результат обновления;
- есть защита от тихой подмены данных;
- расчёт остаётся воспроизводимым.

### 6.3. Что запрещено
Запрещено:
- менять ставки автоматически на клиенте;
- менять ставку без истории;
- менять ставку без логирования;
- подменять ставку постфактум без следа в аудите.

### 6.4. Предпочтительная модель
Предпочтительно:
- автообновление предлагает новую запись;
- администратор подтверждает / отклоняет её;
- либо используется доверенный автоматический режим с журналом и возможностью отката.

## 7. LocalStorage и ключи

### 7.1. Принцип
LocalStorage может содержать только owner-привязанные рабочие ключи.

Корректный вид ключей:
- `abonents_{owner}`
- `payments_{owner}`
- `tariffs_{owner}`
- `ref_rates_{owner}`
- другие owner-bound ключи системы

### 7.2. Запрет
Запрещено:
- хранить общие тарифы без owner-суффикса;
- хранить ставки без owner-суффикса;
- использовать абонента как основной уровень хранения тарифов;
- смешивать данные разных owner в одном и том же ключе.

### 8.1. Backend
Backend обязан:
- вычислять owner только из сессии;

- работать через серверные проверки прав.

## 11. Persist-архитектура (новый этап)

### 11.1. Общий принцип

Система переходит от массовой синхронизации (`uploadNow`) к точечному сохранению (`persist`).

### 11.2. Разделение ответственности

- справочники (tariffs, далее ref_rates):
  → сохраняются через `JKHPersist` (по ключу)

- расчётные данные (abonents, accruals):
  → сохраняются через `uploadNow`

### 11.3. Причина

Разделение:
- уменьшает гонки данных
- устраняет рассинхрон между устройствами
- делает систему предсказуемой

### 11.4. Текущий статус

- tariffs → уже на persist
- accruals → остаются на uploadNow

### 11.5. Ограничение

Полный отказ от uploadNow запрещён до переноса:
- abonents
- payments
- accruals

### 11.6. Запрещено

- смешивать persist и uploadNow для одной сущности
- сохранять тарифы через uploadNow

## 0. Назначение

Этот документ фиксирует изменения, внесённые после стабилизации цепочки:

`server-first load → payments_<ЛС> ledger → autoaccrual → index.html → spravka_sud → upload whitelist`.

Цель документа: не допустить повторного появления уже найденных ошибок:
- пустой индекс после автозагрузки;
- пустая судебная справка при существующем ledger;
- `changed:true` без сохранённого результата;

- отправка legacy/admin/global ключей на `/api/store` и 403.

## 1. Источник истины данных

### 1.1. Backend — главный источник

Серверная БД является главным источником данных.  
Frontend и `localStorage` используются как runtime-cache и транспортный слой.

### 1.2. UI не должен зависеть от успешности upload

Страницы обязаны строиться из локально доступного owner-scoped кэша после server-first загрузки.

Запрещено:
```js
await Data.flushDbToServer();
// и дальше строить UI только если upload успешен
```

Правильно:
```js
try {
  await Data.flushDbToServer();
} catch (e) {
  console.warn('[module] flush failed but continue', e);
}

// UI строится всё равно
rebuildOrRender();
```

Обязательное правило: ошибка sync/upload не должна оставлять `index.html`, `spravka_sud.js` или карточку абонента пустыми, если данные уже есть локально.

## 2. payments_<ЛС> — канонический ledger

### 2.1. Назначение

`payments_<ЛС>` — помесячный ledger абонента. Это не журнал событий, а рабочая таблица начислений/оплат.

В одном месяце допустимы:
- строка начисления;
- одна или несколько строк оплат;
- строки с уточнением оплаты за период.

### 2.2. Минимальная структура строки

Строка ledger должна поддерживать поля:
```js
{
  year: 2025,
  month: 1,
  accrued: 538.00,
  paid: 0,
  paid_date: '',
  id: '...'
}
```

### 2.3. Проверка пригодности ledger

Ledger считается пригодным для пропуска autoaccrual только если есть хотя бы одна строка с:

```js
Number(row.accrued) > 0
```

Важно:
- `paid > 0` без `accrued > 0` НЕ считается полноценным ledger;
- импорт платежей может создать оплаты без начислений;
- в этом случае autoaccrual обязан восстановить начисления.

## 3. Autoaccrual

### 3.1. Назначение

`autoaccrual_engine.js` создаёт/восстанавливает начисления в `payments_<ЛС>`.

### 3.2. Обязательное owner-scoped сохранение

`JKHAutoAccrual.recalcForAbonent(ls)` обязан читать и писать ledger в одном owner-scope:

```js
const ownerId = JKHStore.getOwnerId();
JKHStore.setRaw('payments_' + ls, JSON.stringify(rows), ownerId);
const check = JKHStore.getRaw('payments_' + ls, ownerId);
```

Запрещено:
- писать `payments_<ЛС>` без ownerId;
- читать из одного owner, а писать в другой;
- возвращать `changed:true`, если после расчёта `rows.length === 0`.

### 3.3. Обязательные диагностические логи

После записи:
```js
console.log('[autoaccrual][save]', { id: ls, rowsCount: rows.length, owner: ownerId });
```

После проверки:
```js
console.log('[autoaccrual][after-save]', { id: ls, exists: !!check, len: parsed.length });
```

## 4. index.html

### 4.1. Роль главной страницы

`index.html` не является главным расчётчиком.  
Главная страница — умный читатель ledger.

Правильный порядок:
1. дождаться `JKH_UI_STATE.data.status === ready|empty`;
2. проверить `payments_<uid>`;
3. если ledger пригоден — `skip existing`;
4. если начисления отсутствуют — показать состояние отсутствующих начислений без записи;
5. выполнить `rebuildIndexRows(); render();` без autoaccrual apply и без flush.

### 4.2. Запрещено

Запрещено на главной:
- делать массовый `recalcAll()` без проверки ledger;
- запускать `recalcForAbonent`, autoaccrual apply или любой другой write-side-effect при открытии страницы;
- запускать бесконечный пересчёт при каждом `JKH_UI_STATE_CHANGED`;
- выполнять flush на сервер из read-only просмотра;
- блокировать render из-за ошибки upload;
- считать ledger пригодным только по `paid > 0`.

### 4.3. Обязательная защита от повторов

Должны быть флаги:
- `indexAutoAccrualInFlight`;
- `indexAutoAccrualDoneForOwner`.

Owner учитывается через:
```js
JKHStore.getOwnerId()
```

## 5. spravka_sud.js

### 5.1. Роль судебной справки

Справка суда — производная от ledger. Она не должна менять юридическую логику карточки.

### 5.2. Поведение перед построением

Перед чтением таблицы справка обязана:
1. прочитать `payments_<uid>`;
2. проверить наличие пригодного ledger;
3. если начислений нет — остановить построение справки понятной ошибкой или предложить отдельный подготовительный сценарий начислений;
4. не вызывать `JKHAutoAccrual.recalcForAbonent(ctx.abonentId)` из read-only открытия справки;
5. не выполнять `Data.flushDbToServer()` из read-only открытия справки;
6. построить справку только по уже существующим данным.

### 5.3. Обязательное правило

`SERVER_UPLOAD_FAILED` не имеет права останавливать построение справки, если локальный ledger уже создан и валиден.

Read-only открытие справки не является подготовительным пересчётом: оно не меняет ledger, не запускает autoaccrual apply и не вызывает flush.

## 6. Upload whitelist

### 6.1. Главный принцип

Обычный upload работает только по whitelist.

Запрещён принцип:
> отправить всё, кроме blacklist.

Разрешён принцип:
> отправить только явно разрешённые owner-ключи.

Функция-граница:
```js
_isUploadAllowedKey(baseKey, ownerId)
```

Любой ключ вне whitelist:
- не отправляется;
- логируется;
- не считается ошибкой UI.

Лог:
```js
console.warn('[JKH sync][skip-upload-not-allowed]', key);
```

## 9. Legacy keys

Legacy-ключи допустимы только как read-only/migration fallback.

Примеры:
- `tariffs_dynamic_v1`
- `tariffs_content_repair_v1`
- `tariffs_content_repair_v1_backup`

Если такой ключ найден в localStorage/cache:
- его можно прочитать для миграции;
- его нельзя отправлять на сервер;
- его нельзя использовать как новый источник записи.

## 10. Запрет молчаливого расчёта при отсутствии ставок

Если ставки отсутствуют, повреждены или не покрывают дату расчёта/регистрации/долга:

- расчёт пени / судебной справки должен быть остановлен до исправления данных;

- повреждённый JSON ставок или невалидная структура завершает расчёт кодом `RATES_JSON_INVALID`;
- дата вне покрытия справочника ставок завершает расчёт кодом `MISSING_REQUIRED_RATE`;
- запрещено молча применять первую найденную ставку задним числом;
- запрещено молча считать пеню по ставке `0`.

Это правило распространяется на:

## 15. UID-only Payments + Premise Merge Canon v1.9.0 — 2026-05-03

### 15.1. Главный канон оплат

Лицевой счёт (`ЛС`, `abonentId`, бухгалтерский номер) больше не является техническим ключом оплат.
Он может повторяться у разных исторических и новых абонентов.

Единственный технический ключ оплат — `uid` абонента.

Канонический ключ ledger:

```text
payments_<uid>
```

Запрещено для новых/актуальных абонентов:

```text
payments_<ЛС>
payments_<abonentId>
payments_<accountNumber>
payments_<ls>
```

Все чтение/запись оплат, начислений, autoaccrual, import, карточка абонента, index и calc engine обязаны получать ключ только через канонический резолвер:

```js
window.getPaymentsKeyForAbonent(abonentId)
```

Если ключ не получен — операция чтения/записи ledger блокируется. Нельзя молча падать в `payments_<ЛС>`.

### 15.2. UID обязателен

У каждого абонента должен быть `uid`.

При создании абонента:
- `uid` генерируется всегда;
- нельзя сохранять нового абонента без `uid`;
- повторение ЛС допустимо, повторение UID запрещено.

При нормализации базы (`normalizeDb`) допускается мягкая миграция старых записей без UID:
- абоненту присваивается новый UID;
- старые `payments_<ЛС>` автоматически не переносятся;
- перенос legacy ledger возможен только отдельной осознанной миграцией.

### 15.3. Старые ключи оплат

Старые ключи вида `payments_<ЛС>` могут физически оставаться в localStorage/server storage, но новая логика не имеет права читать их для абонента с UID.

Диагностика legacy-ключей допускается через отдельную функцию, например:

```js
window.JKHDebugListLegacyPaymentKeys()
```

Автоматически удалять старые `payments_<ЛС>` запрещено без отдельного подтверждения/миграционного сценария.

### 15.4. Server-first init для оплаты

`DOMContentLoaded` не имеет права запускать чтение оплат.

Таблица оплат стартует только после готовности данных:

```text
JKH_UI_STATE.data.status === "ready"
```

Правильный порядок:

```text
DATA READY
→ init карточки абонента
→ определение abonent.uid
→ getPaymentsKeyForAbonent(abonentId)
→ чтение payments_<uid>
→ autoaccrual / render
```

Если Data или payment key не готовы:
- не читать storage;
- не создавать пустой ledger по ЛС;
- не писать в `payments_<ЛС>`;
- логировать blocked/read skipped.

### 15.5. Канон объединения квартир

Объединение квартир — отдельная бизнес-операция преобразования объекта недвижимости.

Исходные квартиры выбираются только из списка активных квартир.
Ручной ввод исходных regnum через запятую запрещён.

При объединении минимум двух активных квартир:

1. Старые квартиры:
   - получают `status = "merged"`;
   - получают `closedAt = date объединения - 1 день`;
   - получают `closedReason = "Объединение квартир"`;
   - получают `mergedIntoRegnum = <новый regnum>`;
   - остаются в базе как история.

2. Старые активные links:
   - закрываются `dateTo = closedAt`;
   - старым абонентам ставится `calcEndDate = closedAt`;
   - старые долги, начисления и платежи остаются на старых UID/ledger.

3. Новая квартира:
   - создаётся автоматически как новый объект;
   - получает новый внутренний `regnum` автоматически (`TEMP-YYYYMMDD-XXXX`), если UI не передал допустимый regnum;
   - получает `createdAt = date объединения`;
   - получает `status = "active"`;
   - получает `createdFromMergeRegnums = [старые regnum]`;
   - получает `mergedAt = date объединения`;
   - официальный номер (`officialRegnum`) допускается, но должен быть уникален.

4. Новый абонент:
   - создаётся как новый учётный объект;
   - получает новый ЛС формата `<nextNumeric>-<flat>`;
   - получает новый UID;
   - получает `calcStartDate = date объединения`;
   - получает `calcEndDate = ""`;
   - получает новую активную связь с новой квартирой;
   - копирует от выбранного ответственного только персональные поля: ФИО, телефон, доля, комнаты;
   - не наследует старые платежи и долги.

5. Новый link:

```js
{
  abonentId: newLs,
  regnum: newRegnum,
  dateFrom: mergeDate,
  dateTo: ""
}
```

6. Событие преобразования записывается в `premiseEvents`.
Полную историю преобразований хранить в `premiseEvents`, а в `premises` — только текущий статус и ссылки.

### 15.6. Запрет создания активного абонента на закрытой квартире

Если квартира имеет:

```text
status !== "active"
```

или заполнен:

```text
closedAt
```

то создание нового активного абонента запрещено.

Сообщение:

```text
Квартира закрыта/объединена. Создание нового активного абонента запрещено.
```

Кнопка `абонент+` должна быть disabled/скрыта.
В карточке закрытой/merged квартиры запрещены действия:
- сменить ответственного;
- преобразовать квартиру;
- создать новую активную связь.

### 15.7. UI-видимость исторических объектов

Закрытые/объединённые квартиры и абоненты не удаляются из интерфейса полностью.
Они должны быть видимы как история, но визуально помечены:

```text
объединена
расчёт остановлен
закрыта
```

На главной странице и в списке квартир исторические строки должны быть отделены визуально и не мешать активным объектам.
Активные квартиры выводятся выше merged/closed/archived.

### 15.8. Обязательные регресс-тесты

1. Повторный ЛС:
   - оставить старый `payments_1001`;
   - удалить абонента 1001;
   - создать нового абонента с ЛС 1001;
   - проверить, что новый абонент читает только `payments_<uid>`;
   - старые оплаты не появляются.

2. Объединение квартир:
   - объединить две активные квартиры;
   - старые квартиры стали `merged`;
   - старые абоненты получили `calcEndDate`;
   - новая квартира получила новый regnum;
   - новый абонент получил новый ЛС и UID;
   - новый ledger пустой/создаётся заново по UID.

3. Запрет на closed/merged:
   - попытаться создать абонента на merged-квартире;
   - создание запрещено понятным сообщением.

4. Логи:
   - не должно быть `payments_1001` для нового абонента с UID;
   - должны быть `payments_uid...`;
   - `index`, `payment_table`, `autoaccrual`, `calc_engine`, `import_xls` используют UID-key.

### 15.9. Запреты для будущих задач

Codex запрещено:
- возвращать `payments_<ЛС>` как fallback для абонента с UID;
- запускать чтение оплат на `DOMContentLoaded` до готовности Data;

- перезаписывать старого абонента новой объединённой квартирой;
- создавать активного абонента на `merged/closed` квартире;
- хранить полную историю преобразований внутри `premises` вместо `premiseEvents`.

## 16. Premise Split v1.9.1 — безопасное разъединение квартир / 2026-05-04

### 16.1. Назначение

`Premise Split` — операция разъединения ранее объединённой квартиры или активной объединённой квартиры на несколько самостоятельных квартир.

Split v1 является **структурной операцией**, а не финансовым распределителем.

Главное правило:

```text
Разъединение квартир НЕ переносит долги, оплаты, начисления и пеню автоматически.
```

Долги и платежи старой объединённой квартиры остаются на старом абоненте и старом `payments_<uid>` ledger. Новые квартиры начинают расчёт с даты split.

### 16.2. Разрешённый безопасный сценарий v1

В первой реализации разрешён только безопасный вариант:

1. исходная объединённая квартира закрывается;
2. создаются новые самостоятельные квартиры;
3. для каждой новой квартиры назначается новый или выбранный ответственный абонент;
4. новым абонентам создаются новые UID;
5. новые активные links открываются с даты split;
6. старые долги/платежи/начисления не распределяются автоматически;
7. событие записывается в `premiseEvents`.

### 16.3. Запрещено в v1

В split v1 запрещено:

- автоматически делить задолженность между новыми квартирами;
- автоматически делить оплаты между новыми квартирами;
- переносить старый `payments_<uid>` ledger на новые UID;
- использовать старый ЛС как технический ключ оплат;
- открывать новую активную связь без даты split;
- удалять старую объединённую квартиру из базы;
- удалять старого абонента или его ledger;
- молча создавать split без события в `premiseEvents`;
- выполнять split без явного подтверждения пользователя.

Распределение долга по площади/доле/ручным суммам — отдельная будущая функция и отдельное ТЗ.

### 16.4. Модель данных split

Исходная квартира после split должна получить:

```js
{
  status: "split",
  closedAt: splitDateMinusOne,
  closedReason: "Разъединение квартир",
  splitIntoRegnums: [newRegnum1, newRegnum2],
  splitAt: splitDate
}
```

Новые квартиры должны получить:

```js
{
  regnum: "TEMP-YYYYMMDD-XXXX" или указанный допустимый regnum,
  status: "active",
  createdAt: splitDate,
  createdFromSplitRegnum: oldRegnum,
  splitAt: splitDate,
  city: "...",
  street: "...",
  house: "...",
  flat: "...",
  square: "...",
  officialRegnum: "..."
}
```

Каждый новый/назначенный абонент должен иметь:

```js
{
  uid: новый уникальный UID,
  premiseRegnum: newRegnum,
  regnum: newRegnum,
  calcStartDate: splitDate,
  calcEndDate: ""
}
```

Новый активный link:

```js
{
  abonentId: newAbonentId,
  regnum: newRegnum,
  dateFrom: splitDate,
  dateTo: ""
}
```

### 16.5. Работа со старой объединённой квартирой

При split система обязана:

1. найти активный link исходной квартиры;
2. закрыть его датой `splitDate - 1 день`;
3. поставить старому ответственному абоненту `calcEndDate = splitDate - 1 день`;
4. поставить исходной квартире `status = "split"`;
5. оставить исходную квартиру и старого абонента в базе как исторические объекты;
6. не удалять старые платежи и начисления.

### 16.6. Работа с новыми квартирами

Для каждой новой квартиры система обязана:

1. создать новый `premise` со статусом `active`;
2. проверить уникальность `regnum`;
3. проверить уникальность `officialRegnum`, если он заполнен;
4. создать или назначить ответственного абонента;
5. если создаётся новый абонент — сгенерировать новый UID;
6. создать active link с `dateFrom = splitDate`;
7. не создавать ledger заранее, если нет отдельного расчётного действия;
8. при первом расчёте использовать `payments_<uid>` нового абонента.

### 16.7. Событие premiseEvents

Каждый split обязан записать событие:

```js
{
  id: "split_...",
  type: "split",
  date: splitDate,
  fromRegnums: [oldRegnum],
  toRegnums: [newRegnum1, newRegnum2],
  reason: "...",
  documentNumber: "...",
  documentDate: "...",
  moneyMode: "NO_AUTO_TRANSFER",
  note: "Долги, оплаты, начисления и пеня автоматически не распределялись"
}
```

Полная история split/merge хранится в `premiseEvents`. В `premises` допускаются только текущий статус и ссылки на связанные regnum.

### 16.8. UI-требования

В карточке абонента / квартире должна появиться операция:

```text
Разъединить квартиру
```

Кнопка доступна только если:

- квартира является объединённой или активной объединённой квартирой;
- у пользователя есть право записи;
- данные загружены из конкретного owner, а не из ALL/guest режима.

Перед выполнением обязательно показать предупреждение:

```text
Внимание: долги, оплаты, начисления и пеня исходной квартиры не будут распределены автоматически. Новые квартиры начнут расчёт с даты разъединения.
```

Пользователь должен явно подтвердить действие.

### 16.9. Server-first и сохранение

Split является транзакционной операцией уровня `abonents_db_v1`.

Правильный порядок:

1. сделать snapshot runtime DB;
2. применить split в памяти;
3. выполнить пересчёт только затронутых старых абонентов, если это безопасно;
4. сохранить `abonents_db_v1` локально;
5. выгрузить `abonents_db_v1` на сервер;
6. при ошибке server upload откатить runtime DB к snapshot;
7. показать понятную ошибку.

Запрещено оставлять локально выполненный split, если серверное сохранение не прошло.

## 11. Контракт импорта платежей /api/import/payments/upload_rows

Единый контракт строки платежа:

```json
{
  "account_uid": "UID_...",
  "account_number": "1001",
  "payment_date": "YYYY-MM-DD",
  "payment_period": "YYYY-MM",
  "amount": 123.45,
  "source_index": 1
}
```

Правила:
- frontend может распознавать Excel date в форматах `DD.MM.YYYY` / `YYYY-MM-DD` / serial, но в upload_rows отправляет только `YYYY-MM-DD`;
- backend для upload_rows принимает только `YYYY-MM-DD`;
- `payment_period` обязателен и на сервер отправляется только в `YYYY-MM`;
- импорт платежей не имеет права использовать текущий год как fallback для `payment_period`;
- `source_index` обязателен, целое число `>= 1`;
- backend дополнительно проверяет, что `source_index` существует в `payment_sources_v1`;
- fingerprint платежа строится по `account_uid + payment_date + amount + source_index`;
- одинаковый платёж не применяется повторно: повторный импорт строки с тем же `account_uid`, `payment_date`, `amount` и `source_index` должен быть помечен как `DUPLICATE`/`SKIPPED` и не должен создавать вторую запись в `payments_<uid>`;
- backend является главным валидатором, но frontend не должен отправлять строку вне контракта.

Коды ошибок контракта:

## 12. Import XLS A15 Year Validation and Draft Preview Rule

### 12.1. Расчётный год из A15

- Excel-файл для импорта обязан содержать расчётный год в ячейке `A15` первого листа.
- `A15` пустая — ошибка, импорт блокируется.
- `A15` не является целым годом в диапазоне `1900–2100` — ошибка, импорт блокируется.
- Проверка года выполняется до применения строк и сохраняется в draft предпросмотра.

### 12.2. Проверка дат оплат относительно A15

- Оплата в том же году, что и `A15`, разрешена без предупреждений.
- Оплата в соседнем году (`±1`) разрешена, но отображается как warning.
- Оплата с расхождением больше одного года запрещает импорт.
- Для определения даты оплаты используется существующая нормализация Excel-дат; расчётная логика и timezone-поведение не меняются.

### 12.3. Draft предпросмотра

- `File object` используется только для чтения Excel-файла и не является рабочим состоянием импорта.
- Рабочее состояние импорта — сохранённый preview/draft.
- При наличии валидного draft отсутствие выбранного файла не блокирует продолжение работы.
- Draft обязан сохранять строки предпросмотра, режим, статусы строк, настройки оператора, `parseMeta` и результат проверки A15.
- При возврате на страницу импорт восстанавливает таблицу, строки, статусы и A15 validation из draft.
- Если старый draft не содержит A15 validation, применение блокируется с сообщением: «Черновик устарел. Требуется повторная загрузка файла для проверки года.»
- Предпросмотр очищается только явной кнопкой «Сбросить предпросмотр».
- После применения строк таблица не очищается: применённые строки помечаются как «применено», остальные остаются в предпросмотре.

## 13. Жизненный цикл объекта квартиры: временный → зафиксированный

### 13.1. Временный объект

- `regnum` вида `TEMP-*` является временным номером объекта.
- Пока `officialRegnum` пустой, временный объект допускает штатное редактирование адресных и идентификационных полей в существующем UI.
- Защита сохранения всё равно выполняется в `premises_admin.js`; UI `disabled` не считается достаточной защитой.

### 13.2. Фиксация объекта

- Заполнение `officialRegnum` (кадастрового / официального номера) фиксирует объект квартиры.
- Для зафиксированного объекта после создания запрещено менять идентичность:
  - `officialRegnum`;
  - `regnum`;
  - `createdAt`;
  - `city`;
  - `street`;
  - `house`;
  - `flat`.
- После фиксации разрешено менять только `square`.
- Если нужно изменить адрес, дату создания, дом, квартиру или идентификационный номер, это не редактирование существующего объекта: нужно закрыть старый объект, создать новый объект и создать новую связь ответственности.

### 13.3. Переход из Excel-импорта для изменения площади

- Переход из Excel-импорта для изменения площади обязан проверять связку: `UID + ЛС + ФИО + active link + regnum`.
- UID является главным идентификатором импортируемой строки. ЛС/ФИО используются как контрольная проверка. Различия форматирования ФИО, регистра, пробелов, ё/е, неполного отчества или формы записи ФИО не являются основанием для критической блокировки, если UID найден и active link/regnum структурно подтверждены.
- Один `regnum` из URL не является достаточным основанием для редактирования квартиры.
- URL из импорта должен передавать контрольный контекст `from=import`, `regnum`, `uid`, `ls`, `fam`, `excelRow`, `excelSquare`.
- Перед открытием формы и перед сохранением площадь можно менять только если активная связь `links` подтверждает, что квартира с данным `regnum` принадлежит абоненту из строки Excel.
- В режиме открытия из Excel-импорта разрешено менять только `square`; изменение адреса, даты создания, `regnum` или `officialRegnum` должно блокироваться даже при ручной разблокировке полей через DevTools.

## 14. Единый индикатор процесса и возврат из Excel-импорта

- Все длительные операции загрузки, сохранения, пересчёта и применения импорта должны сопровождаться визуальным индикатором процесса. Пользователь не должен видеть молчаливое зависание интерфейса.
- Индикатор процесса должен скрываться через `finally`, чтобы ошибка операции не оставляла интерфейс в состоянии вечной загрузки.
- Индикатор процесса обязан исчезать после завершения операции даже тогда, когда предпросмотр или импорт содержат ошибки данных в отдельных строках. Ошибки данных показываются в статусах строк, но не являются причиной держать глобальный spinner.
- Текст «Загрузка данных…» используется только во время реальной загрузки данных; проверка Excel, применение первички, добавление платежей и создание абонента должны показывать собственный текст операции.
- После создания абонента из Excel-импорта при возврате на `import_xls.html` должно показываться сообщение с номером строки Excel и UID созданного абонента.
- UID из Excel и UID, созданный системой, являются разными понятиями:
  - `row.excelUid` / `row.uid` — исходный UID из Excel;
  - `row.createdUid` — UID абонента, созданный программой;
  - `row.resolvedUid` — UID, который можно использовать для внутренних операций после создания.
- Предпросмотр не должен подменять пустой Excel UID системным UID без явной пометки. Если UID в Excel был пустой, но абонент создан, в колонке UID нужно показывать «В Excel UID пусто» и «Создан UID: ...».
- При возврате из создания абонента Excel-preview/draft должен восстановиться; целевая строка должна сохранить пустой исходный Excel UID и отдельно сохранить `createdUid`/`resolvedUid` для продолжения импорта платежей.

## 15. P0 Silent-fallback audit closure — 2026-05-08

Этот раздел закрывает P0 silent-fallback audit и имеет приоритет над более ранними формулировками этого файла, если они допускали молчаливый fallback.

### 15.1. Read-only pages

Открытие справки, главной страницы и таблицы платежей является read-only действием.

Запрещено при обычном открытии этих страниц:
- изменять `payments_<uid>` ledger;
- запускать autoaccrual apply;
- вызывать flush / upload на сервер;
- маскировать отсутствие начислений созданием строк без явного пользовательского подготовительного действия.

### 15.2. Ledger integrity

Если ключ `payments_<uid>` существует, его содержимое должно быть валидным JSON-массивом.

Fatal-правила:
- повреждённый JSON ledger завершает операцию кодом `LEDGER_JSON_INVALID`;
- JSON, который распарсился, но не является массивом, также завершает операцию кодом `LEDGER_JSON_INVALID`;
- запрещено возвращать `[]` как fallback для существующего, но повреждённого ledger.

### 15.3. Refinancing rates

Расчёт пени требует полного и валидного справочника ставок на дату расчёта.

Fatal-правила:
- ставки отсутствуют: `RATES_MISSING`;
- JSON ставок повреждён или структура невалидна: `RATES_JSON_INVALID`;
- дата не покрыта справочником ставок: `MISSING_REQUIRED_RATE`;
- запрещено считать по ставке `0` как fallback.

### 15.4. Exclusion periods

`exclude_periods_<abonentId>` влияет на расчёт пени и не может молча игнорироваться при повреждении.

Fatal-правила:
- повреждённый JSON исключений: `EXCLUDES_JSON_INVALID`;
- невалидные даты или интервалы исключений: `EXCLUDES_INVALID`;
- запрещено считать так, как будто исключений нет, если ключ исключений существует, но повреждён или невалиден.

### 15.5. Fake dates forbidden

Дата `2000-01-01` запрещена как fallback для финансовых и судебных дат.

Fatal-правила:
- отсутствует дата начала расчёта: `START_DATE_MISSING`;
- отсутствует дата начала ответственности: `RESPONSIBILITY_DATE_MISSING`;
- запрещено подставлять искусственную дату вместо отсутствующей даты начала ответственности, расчёта, долга или судебного периода.

### 15.6. Import period

Импорт платежей требует явный `payment_period` в формате `YYYY-MM`.

Запрещено:
- выводить `payment_period` из текущего года;
- использовать текущую дату или год запуска импорта как fallback;
- применять строку платежа без явного периода.

### 15.7. Debt transfer

Перенос долга в режиме `WITH_DEBT` разрешён только после успешного frozen debt calculation.

Fatal-правила:
- ошибка расчёта frozen debt останавливает перенос долга;
- повреждённый JSON frozen debt останавливает перенос долга;
- запрещено превращать ошибку расчёта или JSON в `principal: 0` / `penalty: 0`;
- безопасный перенос без долга должен быть выбран явно и не является fallback из ошибочного `WITH_DEBT`.

## Financial Canon: Responsibility Transfer

Единая передача ответственности по квартире является финансовым каноном и выполняется только через канонический transfer-flow.

Обязательные правила:

1. Создание нового абонента на квартиру с активным `link` запрещено без transfer-flow.
2. Если квартира уже имеет активного ответственного, система должна использовать только `Data.transferResponsibility(...)`.
3. Разрешены только базовые режимы:
   - `WITH_DEBT`;
   - `WITHOUT_DEBT` / `NO_DEBT`.
4. При transfer:
   - старый `link.dateTo = transferDate - 1`;
   - старый `abonent.calcEndDate = transferDate - 1`;
   - новый `link.dateFrom = transferDate`;
   - новый `abonent.calcStartDate = transferDate`.
5. `WITH_DEBT`:
   - требует успешного frozen debt calculation;
   - при ошибке расчёта transfer блокируется;
   - нулевой долг допустим только при `success: true`;
   - создаётся `jkh_transfer_balance_v1`.
6. `WITHOUT_DEBT` / `NO_DEBT`:
   - долг остаётся на старом `payments_<oldUid>`;
   - новый абонент получает новый UID;
   - новый ledger `payments_<newUid>` стартует с нуля;
   - transfer balance не создаётся либо очищается.
7. UI запрещено:
   - самостоятельно считать долг;
   - читать `payments_<ЛС>`;
   - писать `jkh_transfer_balance_v1`;
   - глушить ошибки расчёта;
   - вручную закрывать/открывать links при смене ответственного.
8. Преобразование квартиры без назначения нового абонента не является transfer-flow:
   - новая квартира создаётся как структурный объект;
   - active link не создаётся;
   - начисления не начинаются;
   - долги/платежи/пени не переходят автоматически;
   - событие фиксируется в `premiseEvents`.

### 15.10. Исключённые периоды расчёта пени

Канонический источник истины для исключённых периодов расчёта пени — ключ `exclude_periods_<abonentId>` в storage.

Правила хранения и применения:
- формат значения: JSON array;
- объект периода: `{from:"YYYY-MM-DD", to:"YYYY-MM-DD", reason:"string"}`;
- исключённые периоды влияют только на расчёт пени;
- основной долг исключёнными периодами не изменяется;
- поле абонента `defaultExcludes` является legacy/cache и не используется как источник истины для расчёта;
- при отсутствии `exclude_periods_<abonentId>` legacy `defaultExcludes` может использоваться только как read-only migration source, после чего должен быть записан валидный JSON-массив в `exclude_periods_<abonentId>`;
- canonical key `exclude_periods_<abonentId>` никогда не может хранить пустую строку;
- отсутствие исключённых периодов хранится только как `[]`;
- пустая строка в существующем canonical key считается повреждением данных и подлежит repair только при точном `raw === ""`;
- repair пустой строки обязан заменить значение на `[]` и не должен молча лечить другой битый JSON, например `{`;
- transfer/merge/create нового абонента не копирует исключённые периоды старого абонента (`defaultExcludes`, `excludes`, `excludePeriods`, `specialExcludes`);
- новый абонент стартует с `exclude_periods_<newAbonentId> = []`;
- повреждённый canonical JSON в `exclude_periods_<abonentId>` блокирует расчёт пени до исправления;
- запрещено хранить пустую строку вместо JSON-массива.

## 16. Canonical Financial Modes

Единый финансовый слой нужен, чтобы все операции с ledger, frozen debt и transfer balance проходили через один проверяемый write-path и не расходились между страницами UI.

Правила:
- UI не имеет права самостоятельно считать долг, balance, frozen debt или transfer balance.
- UI не имеет права напрямую писать financial ledger.
- Единственный write-path ledger: `payments_<uid>`.
- `payments_<LS>` разрешён только как read-only legacy fallback внутри service layer.
- `Data.resolvePaymentLedgerKey(abonentOrId)` определяет canonical key по UID.
- `Data.readPaymentLedger(abonentOrId)` является canonical ledger reader и единственным местом, где допустим legacy read fallback.
- `Data.writePaymentLedger(abonentOrId, rows, options)` является canonical ledger writer и обязан блокировать запись в `payments_<LS>`, если LS не является UID.
- `Data.createEmptyPaymentLedger(abonentOrId)` создаёт пустой ledger нового абонента только через canonical writer.
- `Data.normalizeFinancialMode(mode)` нормализует режимы `WITH_DEBT`, `WITHOUT_DEBT`; входной alias `NO_DEBT` считается `WITHOUT_DEBT`.
- `Data.transferResponsibility(...)` является canonical transfer entrypoint.
- Frozen debt (`jkh_frozen_debt_v1:*`) и transfer balance (`jkh_transfer_balance_v1:*`) создаются только service layer.
- `jkh_freeze_to_v1:*` и `jkh_transfer_to_v1:*` записываются только service layer в рамках transfer transaction.
- Financial event log обязателен для ledger/transfer write-path и хранит минимум: `type`, `mode`, `sourceAbonentId`, `targetAbonentId`, `premiseId/regnum`, `date`, `ownerId`, `createdAt`, `debtAmount`, `balanceAmount` при наличии.
- Merge/split должны быть приведены к тому же responsibility transaction boundary; `SPLIT_PREMISES` пока является документированным будущим режимом без бизнес-логики split.
