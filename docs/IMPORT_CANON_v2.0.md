# IMPORT_CANON_v2.0 (ПАПАЖКХ)

Версия: **v2.0.0**  
Дата фиксации: **2026-04-23**  
Статус: **АКТУАЛЬНЫЙ КАНОН ИМПОРТА EXCEL**

---

## 0. Назначение документа

Этот документ фиксирует обязательный канон импорта Excel для:
- шага 1 — первичка;
- шага 2 — платежи;
- preview / validate / apply;
- антидубля и серверного проведения платежей.

Если `IMPORT_CANON_v1.6.md` противоречит этому документу, приоритет у `IMPORT_CANON_v2.0.md`.

---

## 1. Общие правила импорта

### 1.1. Источник истины
- Backend / сервер — источник истины.
- Frontend / import_xls.html — только интерфейс предпросмотра, запуска и показа статусов.

### 1.2. Обязательные стадии
Любой импорт проходит стадии:
1. upload
2. parse
3. validate
4. apply

Запрещено проводить платежи напрямую из браузера минуя серверный apply.

### 1.3. Предпросмотр обязателен
До записи всегда должен существовать preview со строковыми статусами и причинами.

### 1.4. Роли
- Guest не может импортировать.
- Admin в ALL-mode не может импортировать.
- User/Admin в своей owner-базе может импортировать при разрешённой записи.

---

## 2. Канон первички

### 2.1. Header и mapping
Первичка должна поддерживать:
- auto-detect header;
- multi-row header;
- fallback на field-map только если auto-detect не дал валидную структуру.

### 2.2. Обязательные поля первички
Для строки первички обязательны:
- ЛС
- Фамилия
- Общая площадь

UID желателен и должен использоваться, если присутствует.

### 2.3. Поиск абонента в первичке
- Если есть UID → сначала поиск по UID.
- Если UID нет → допускается поиск по ЛС + Фамилии.
- Если совпадений 0 → ошибка или создание абонента по явному разрешению.
- Если совпадений >1 → ошибка неоднозначности.

### 2.4. Создание абонента
Создание абонента из preview возможно только:
- если UID отсутствует;
- если ЛС/ФИО достаточны;
- если включено явное разрешение на создание.

### 2.5. Начисления
Начисления не импортируются как готовые суммы долга.
Они считаются системой автоматически на основании:
- тарифов owner;
- площади абонента.

## 3. Канон платежей

### 3.1. Жёсткое правило допуска
**Платежи могут учитываться только если есть UID.**

Это обязательный канон:
- без UID платёж не проводится;
- fallback-проведение только по ЛС/Фамилии запрещено;
- отсутствие UID = invalid/failed.

### 3.2. Для apply платежей обязательны оба поля
Для серверного проведения платежа обязательны:
- `account_uid`
- `account_number` (ЛС)

Смысл:
- UID — допуск к учёту платежа;
- ЛС — адрес записи в текущем ledger storage.

### 3.3. Нормализация платежа
Перед validate/apply значения должны быть приведены к канону:
- paid_date → `YYYY-MM-DD`
- payment_period → `YYYY-MM`
- amount → Decimal с 2 знаками
- source_index → int >= 1
- account_uid → trimmed string
- account_number → trimmed string

### 3.4. Legacy ledger
Несмотря на серверную нормализацию:
- fingerprint и SQL-слой используют каноническую дату `YYYY-MM-DD`;
- текущий KV/JSON ledger пока остаётся совместимым с legacy-форматом `DD.MM.YYYY`;
- storage key текущего ledger остаётся `payments_<ЛС>`.

Запрещено:
- писать ledger в `payments_<UID>`;
- подменять отсутствующий ЛС значением UID;
- подменять отсутствующий UID значением ЛС.

---

## 4. Fingerprint и антидубль

### 4.1. Обязательный fingerprint-lock
Антидубль должен работать на сервере через fingerprint-lock.

### 4.2. Состав fingerprint
Fingerprint платежа строится из нормализованных значений:
- owner_id
- account_uid
- account_number
- paid_date
- amount
- source_index
- payment_period

### 4.3. Требование к уникальности
Один и тот же платеж не должен проводиться второй раз в одной owner-базе.

Гарантия обеспечивается:
- серверным кодом;
- SQL UNIQUE по `(owner_id, import_type, fingerprint)`.

### 4.4. Что считается дублем
Если fingerprint уже присутствует в `import_applied_fingerprints`, строка должна получить:
- status = `duplicate`
- reason_code = `DUPLICATE_FINGERPRINT`
- понятный reason_text

### 4.5. Запрет
Запрещено считать антидубль только на клиенте.

---

## 5. Validate и статусы строк

### 5.1. Обязательные статусы
Минимально допустимые статусы строк:
- parsed
- invalid
- ready
- applied
- duplicate
- failed

### 5.2. Обязательная причина
Для `invalid`, `duplicate`, `failed` обязательно заполнять:
- reason_code
- reason_text

### 5.3. UID-правило в validate
Если `account_uid` пустой:
- status = `invalid`
- reason_code = `ACCOUNT_UID_REQUIRED`
- reason_text = `Платежи могут учитываться только при наличии UID`

### 5.4. ЛС-правило в validate
Если `account_number` пустой:
- status = `invalid`
- reason_code = `ACCOUNT_NUMBER_REQUIRED`
- reason_text = `Для записи в ledger нужен лицевой счёт`

---

## 6. Apply платежей

### 6.1. Где выполняется apply
Apply выполняется только на сервере.

### 6.2. Порядок apply
Для каждой строки `ready`:
1. нормализация;
2. сбор fingerprint;
3. попытка зарезервировать fingerprint в SQL;
4. если fingerprint уже есть → duplicate;
5. если fingerprint новый → запись в текущий ledger storage;
6. строка получает applied / duplicate / failed.

### 6.3. Транзакционность
Минимальная гарантия:
- резерв fingerprint и запись платежа должны быть атомарны на уровне строки.

Если проект использует row-level nested transaction, это допустимо, но должно быть зафиксировано как осознанная модель.

### 6.4. Summary apply
Apply обязан возвращать summary:
- applied_count
- duplicate_count
- failed_count
- skipped_count

---

## 7. Запрещённые действия при импорте

Запрещено:
- проводить платежи без UID;
- тихо подменять UID/ЛС друг другом;
- писать платежи в storage по UID вместо ЛС;
- удалять существующие данные импортом;
- чистить базы импортом;
- менять тарифы/ставки/реквизиты импортом платежей;
- проводить apply только на клиенте.

---

## 8. Обязательные проверки после изменений

После правок импорта обязательно проверить:

1. строка без UID не проводится;
2. строка с UID и ЛС проводится;
3. первый импорт файла проводит платежи;
4. повторный импорт того же файла даёт duplicate, а не дубль в ledger;
5. storage key остаётся `payments_<ЛС>`;
6. ledger paid_date остаётся совместимой с legacy-форматом;
7. preview показывает корректные статусы и причины;
8. owner isolation не нарушена.

---

## 9. Итоговый канон

### Для первички
- допускается идентификация по UID или по ЛС+Фамилии.

### Для платежей
- допускается учёт только при наличии UID;
- apply только через сервер;
- антидубль только через fingerprint-lock;
- ledger storage пока остаётся legacy-совместимым.
