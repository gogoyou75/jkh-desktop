# Граница LocalStorage ↔ База данных (ПАПАЖКХ)

Дата фиксации: **2026-03-25**  
Статус: **АКТУАЛИЗИРОВАНО**

---

## 1. Общий принцип

**LocalStorage — не база данных.**  
LocalStorage используется как:
- офлайн-хранилище;
- кэш;
- черновик;
- транспортный слой для sync.

**Сервер / БД — источник истины.**  
Сервер отвечает за:
- owner-изоляцию;
- права доступа;
- консистентность;
- аудит;
- историю изменений.

---

## 2. Что хранится в LocalStorage

### 2.1. UI и сессия
- состояние интерфейса;
- фильтры, сортировки, поиск;
- позиция скролла;
- технические кэш-данные.

### 2.2. Рабочие owner-данные
Допускается хранение рабочей копии:
- абонентов;
- квартир / premises;
- начислений;
- платежей;
- тарифов;
- ставок;
- исключённых периодов;
- связанных owner-справочников.

Но все такие данные — **не юридический источник**, а рабочая копия.

### 2.3. Черновики и очередь операций
- несинхронизированные изменения;
- очередь sync;
- временные результаты импорта.

---

## 3. Что хранится на сервере / в БД

### 3.1. Пользователи и права
- users
- roles
- permissions
- статус пользователя
- серверная сессия

### 3.2. Основные сущности
- Abonent
- Premises / links
- Payment
- Accrual
- Tariff
- RefinanceRate
- ExclusionPeriod
- Organization

### 3.3. Аудит и история
- логи операций;
- история изменений;
- история ставок;
- история тарифов;
- сообщения об ошибках ставок;
- результаты автообновления ставок.

---

## 4. Критическое правило owner

### 4.1. Источник owner
`owner` определяется только на сервере из сессии.

### 4.2. Запрет
Нельзя доверять owner, который пришёл:
- из frontend;
- из localStorage;
- из query/body;
- из скрытого поля формы.

### 4.3. Все операции
Все серверные операции:
- load
- save
- delete
- sync
- dump

выполняются только с фильтрацией по owner.

---

## 5. Правило ключей LocalStorage

Все рабочие ключи owner-данных должны быть owner-bound.

Корректные примеры:
- `abonents_{owner}`
- `payments_{owner}`
- `tariffs_{owner}`
- `ref_rates_{owner}`

Некорректно:
- хранить общие тарифы без owner;
- хранить ставки как глобальный ключ без owner;
- делать тарифы частью персональной базы отдельного абонента.

---

## 6. Тарифы и ставки

### 6.1. Тарифы
Тарифы:
- принадлежат owner;
- общие для всех абонентов owner;
- редактируются только администратором;
- для user — только просмотр.

### 6.2. Ставки
Ставки рефинансирования:
- принадлежат owner;
- применяются ко всем его абонентам;
- редактируются только администратором;
- для user — только просмотр.

### 6.3. Сообщение об ошибке
user может отправить сообщение об ошибке ставки, но не может менять саму ставку.

---

## 7. Будущее автообновление ставок

Автообновление ставок из интернета допускается только как серверный механизм.

Обязательные условия:
- логирование;
- история;
- фиксирование источника;
- безопасный откат / контроль.

Запрещено автoобновление ставок на клиенте.

---

## 8. Практический вывод для реализации

Frontend может:
- показывать данные;
- редактировать только то, что разрешено ролью;
- работать с локальным кэшем.

Backend обязан:
- окончательно проверять права;
- окончательно определять owner;
- быть источником истины для sync.
