# TASK_FOR_CODEX_PAYMENTS_SERVER_FIRST.md

## Задача

Добавить и проверить систему ручного добавления оплаты в server-first архитектуре ПАПАЖКХ.

## Контекст

Проект уже перешёл к server-first канону: backend / MySQL / `kv_store` — источник истины, frontend cache (`JKHStore`, localStorage) — только рабочая копия.

Оплаты должны храниться совместимо с существующей моделью:

```text
payments_<abonentId_or_ls>
```

Нельзя создавать вторую модель оплат.

## Что нужно сделать

1. Найти текущую страницу/модуль карточки абонента, где редактируются платежи.
2. Проверить, как сейчас добавляется строка оплаты.
3. Убедиться, что добавление оплаты идёт через единый массив `payments_<id>`.
4. Если ручного добавления оплаты нет или оно не server-first — добавить безопасный сценарий:
   - создать строку оплаты;
   - валидировать сумму, дату, месяц, год, источник;
   - пересчитать задолженность/пеню существующим расчётным движком;
   - записать в `JKHStore`;
   - выполнить `Data.flushDbToServer()`;
   - при ошибке откатить snapshot.
5. Убедиться, что после перезагрузки страницы оплата остаётся.
6. Убедиться, что после входа с другого компьютера под тем же пользователем оплата видна.

## Жёсткие запреты

Не менять:

- MySQL-пароли;
- docker-compose;
- backend без необходимости;
- owner-модель;
- calc_engine.js без отдельного основания;
- структуру импорта без совместимости.

Запрещено:

- сохранять оплату только в localStorage;
- делать прямой `localStorage.setItem('payments_...')` как финальное сохранение;
- показывать успех до server flush;
- смешивать оплаты разных owner;
- затирать старые годы при добавлении нового года.

## Обязательная проверка server-first

После добавления оплаты:

1. открыть DevTools;
2. убедиться, что нет JS-ошибок;
3. перезагрузить страницу;
4. проверить, что оплата осталась;
5. выполнить server dump / загрузку с сервера;
6. проверить, что ключ `payments_<abonentId>` содержит новую строку.

## Дополнительная проверка импорта оплат

Проверить, что импорт оплат из Excel пишет в ту же модель, что и ручная оплата.

Особенно проверить файл, где колонки 1–77 образуют месячные блоки, а за месяц может быть до трёх источников оплаты:

- сумма оплаты;
- дата оплаты;
- сумма оплаты другим методом;
- дата оплаты другим методом;
- сумма оплаты через расчётный счёт;
- дата оплаты через расчётный счёт.

Импорт за новый год должен добавлять данные нарастающе, а не затирать предыдущий год.

## Результат от Codex

Codex должен выдать:

1. полный список изменённых файлов;
2. краткое объяснение логики;
3. проверку ручного добавления оплаты;
4. проверку сохранения через сервер;
5. проверку после перезагрузки;
6. отдельно указать, затронут ли импорт оплат.
