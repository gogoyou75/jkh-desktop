# PAYMENTS_SERVER_FIRST_CANON.md

Версия: **v1.0 — 2026-04-25**  
Статус: **КАНОН УЧЁТА ОПЛАТЫ ЧЕРЕЗ СЕРВЕР**

---

## 1. Цель

Зафиксировать правильную систему добавления, редактирования, удаления и импорта оплат в server-first архитектуре ПАПАЖКХ.

Главный принцип: серверная база — источник истины; localStorage / JKHStore на клиенте — рабочий кэш и транспортный слой.

---

## 2. Где живут оплаты

Текущая совместимая модель хранения:

```text
payments_<abonentId_or_ls>
```

Значение — JSON-массив строк оплаты/начислений.

Пример ключа:

```text
payments_1001
```

В server-first режиме этот ключ должен сохраняться в серверном `kv_store` в owner-контексте.

---

## 3. Owner-контекст

Любая операция с оплатами выполняется только в owner-контексте серверной сессии.

Запрещено:

- брать owner из query string;
- брать owner из формы;
- сохранять оплату в чужой owner-пространство;
- использовать прямой `localStorage.setItem()` как источник истины.

---

## 4. Минимальная структура строки оплаты

Строка оплаты должна поддерживать поля:

```js
{
  id,
  month,
  year,
  accrued,
  paid,
  paid_date,
  source,
  note,
  use_period,
  period_from_m,
  period_from_y,
  period_to_m,
  period_to_y,
  pay_main,
  pay_penalty,
  total_debt
}
```

Где:

- `paid` — сумма оплаты;
- `paid_date` — фактическая дата оплаты;
- `source` — источник оплаты;
- `use_period` — оплата относится к периоду и влияет на пеню;
- `period_*` — период, за который учитывается оплата;
- `accrued` — начисление месяца;
- `pay_main`, `pay_penalty`, `total_debt` — расчётные поля, не должны вручную подменять расчётную логику.

---

## 5. Система добавления оплаты

Правильный сценарий пользовательского добавления оплаты:

1. Пользователь нажимает `Добавить оплату`.
2. UI создаёт новую строку в `payments_<abonentId>` в runtime-массиве.
3. Строка валидируется:
   - сумма больше 0;
   - дата оплаты валидна;
   - год/месяц валидны;
   - источник оплаты допустим;
   - если `use_period=true`, период заполнен корректно.
4. Расчётная логика вызывается только через существующие движки проекта.
5. Данные записываются в `JKHStore` через `setJSON`/`setRaw`.
6. Выполняется `Data.flushDbToServer()` или эквивалентный server-first flush.
7. UI показывает успех только после успешной серверной записи.

---

## 6. Транзакционность

Добавление оплаты должно быть атомарным на уровне UI:

- сделать snapshot текущего массива оплат;
- применить изменение;
- выполнить перерасчёт;
- сохранить на сервер;
- при ошибке вернуть snapshot.

Запрещено показывать `Сохранено`, если серверный flush не прошёл.

---

## 7. Перерасчёт

После добавления/изменения/удаления оплаты обязательно:

- пересчитать задолженность;
- пересчитать пеню, если дата оплаты или период оплаты влияет на просрочку;
- не считать пеню внутри UI-обработчика, если для этого есть расчётный движок.

Критическое правило: расчёт задолженности и пени не должен расползаться по страницам.

---

## 8. Источники оплаты

Источники оплаты должны храниться как справочник owner-уровня, например:

```text
payment_sources_v1
```

Минимальная модель:

```js
{ id, title, active, sort }
```

На уровне Excel-импорта допускаются фиксированные колонки трёх источников оплаты за месяц. Они должны маппиться на справочник источников, а не создавать отдельную бизнес-логику.

---

## 9. Импорт оплат

Импорт оплат из Excel должен приводить данные к той же модели, что и ручное добавление оплаты.

Запрещено иметь две несовместимые модели:

- ручная оплата отдельно;
- импортированная оплата отдельно.

Итог импорта — те же `payments_<abonentId>` строки, с batch/audit-метаданными при необходимости.

---

## 10. Серверная проверка после сохранения

После добавления оплаты нужно уметь проверить, что данные реально попали на сервер:

1. выполнить flush;
2. заново получить `store_dump`;
3. проверить наличие `payments_<abonentId>`;
4. убедиться, что добавленная строка есть после перезагрузки страницы.

---

## 11. Запрещённые сценарии

Запрещено:

- сохранять оплату только в localStorage;
- делать ручную кнопку `Сохранить на сервер` как основной сценарий;
- делать перерасчёт после сохранения вместо перерасчёта до flush;
- терять оплату при перезагрузке;
- смешивать оплаты разных owner;
- затирать старый год новым импортом;
- затирать строки одного источника строками другого источника.

---

## 12. Регрессия

Проверить вручную:

1. Добавить оплату абоненту.
2. Перезагрузить страницу.
3. Убедиться, что оплата осталась.
4. Зайти с другого компьютера под тем же пользователем.
5. Убедиться, что оплата видна.
6. Проверить, что задолженность пересчиталась.
7. Проверить, что пеня пересчиталась корректно.
8. Проверить, что импорт оплаты за другой год не затирает предыдущий год.

---

## 13. Критерий готовности

Система добавления оплаты считается готовой только если ручная оплата и импорт используют один и тот же ledger `payments_<abonentId>` и сохраняются через server-first flush.
