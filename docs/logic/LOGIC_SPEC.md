## 0. Назначение документа

Этот документ фиксирует обязательную архитектуру и права доступа для:
- тарифов;
- ставок рефинансирования;
- изоляции данных по owner;
- синхронизации данных между устройствами;
- будущего автoобновления ставок с сервера.

Если старые документы противоречат этому файлу, приоритет у этого файла и у `docs/critical/CRITICAL_CHANGELOG.md`.

---

## 1. Ownership и изоляция данных (CRITICAL)

### 1.1. Общее правило
Все рабочие данные системы принадлежат конкретному `owner` (user_id).

К сущностям owner-пространства относятся:
- abonents
- payments
- accruals
- tariffs
- refinance_rates
- exclusion_periods
- premises / links
- notes / calc periods / report periods / related service data

### 1.2. Источник owner
`owner` определяется **только сервером** из серверной сессии.

Запрещено:
- передавать owner с клиента как источник истины;
- доверять owner из localStorage, query string, body, hidden fields;
- выполнять save/load/delete/sync без серверного owner.

### 1.3. Последствие
Каждый пользователь работает только со своей базой.  
Данные разных пользователей полностью изолированы.

---

## 2. Источник истины и синхронизация

### 2.1. Источник истины
- **Backend / серверная БД** — источник истины.
- **Frontend / localStorage** — рабочий кэш, офлайн-копия и транспортный слой.

### 2.2. Синхронизация
После логина и при явной загрузке с сервера клиент должен иметь возможность получить **полный набор данных owner**.

Минимальное требование:
- сервер поддерживает выгрузку полного набора ключей owner (`store_dump` или эквивалент);
- клиент умеет восстановить локальную рабочую копию из серверного набора.

### 2.3. Критический дефект
Если тарифы или ставки не синхронизируются между двумя устройствами одного owner, это считается **критической ошибкой синхронизации**.

---

## 3. Тарифы

### 3.1. Модель
Тарифы являются сущностью уровня `owner`.

Правильно:
- у каждого пользователя своя независимая база тарифов;
- один набор тарифов действует для всех абонентов этого пользователя;
- тарифы не принадлежат отдельному абоненту.

Неправильно:
- хранить тарифы на уровне конкретного абонента;
- дублировать один и тот же тариф по каждому абоненту;
- менять логику так, чтобы тариф был частью карточки абонента как первичный источник.

### 3.2. Структура
Тариф хранится как историческая запись:
- tariff_content
- tariff_repair
- start_date

Правило:
- последний тариф действует до появления нового;
- тариф вводится с начала месяца;
- один месяц имеет одну актуальную тарифную запись на owner-уровне.

### 3.3. Права доступа
- **Администратор**: создание / редактирование / удаление тарифов.
- **Пользователь**: только просмотр (`read-only`).

### 3.4. Применение
Начисление абонента считается по формуле:

`начисление = тарифы owner × площадь абонента`

Абонент хранит:
- площадь;
- адресные и идентификационные данные;
- свою финансовую историю.

Абонент **не хранит собственный тарифный справочник**.

---

## 4. Ставка рефинансирования

### 4.1. Модель
Ставки рефинансирования являются сущностью уровня `owner`.

Они:
- общие для всех абонентов данного пользователя;
- применяются в расчёте пени ко всем его абонентам;
- хранятся как история по датам.

### 4.2. Жёсткое правило прав доступа
**Изменять ставки рефинансирования может только администратор.**

Права:
- **Администратор**: полный CRUD.
- **Пользователь**: только просмотр (`read-only`), без права изменения.

Любая попытка изменения ставки от роли `user` должна завершаться отказом доступа.

### 4.3. Пересчёт
После изменения ставки:
- система должна инициировать корректный пересчёт пени;
- перерасчёт должен быть воспроизводимым и аудируемым;
- история прежних ставок обязана сохраняться.

### 4.4. Логирование
Каждое изменение ставки должно логироваться минимум с полями:
- user_id / actor_id
- старая ставка
- новая ставка
- дата изменения
- тип изменения
- источник изменения (manual / import / auto-update)

---

## 5. Сообщение об ошибке ставки

### 5.1. Назначение
Пользователь не меняет ставку напрямую, но может отправить сигнал:
**«ошибка в ставке рефинансирования»**.

### 5.2. Минимальная модель
Сообщение должно содержать:
- type = `refinance_rate_issue`
- text
- created_at
- user_id / owner
- optional related_date

### 5.3. Смысл
Разделение обязанностей:
- изменение справочника ставок — только администратор;
- сообщение о возможной ошибке — пользователь.

---

## 6. Будущее автообновление ставок из интернета

### 6.1. Разрешённое направление развития
В дальнейшем допускается автоматическое обновление ставок из внешнего источника:
- через API;
- через серверный парсер;
- через контролируемый AI-assisted механизм.

### 6.2. Ограничения
Такое обновление допускается **только на сервере** и только при соблюдении правил:
- сохраняется история всех значений;
- фиксируется источник данных;
- логируется время и результат обновления;
- есть защита от тихой подмены данных;
- расчёт остаётся воспроизводимым.

### 6.3. Что запрещено
Запрещено:
- менять ставки автоматически на клиенте;
- менять ставку без истории;
- менять ставку без логирования;
- подменять ставку постфактум без следа в аудите.

### 6.4. Предпочтительная модель
Предпочтительно:
- автообновление предлагает новую запись;
- администратор подтверждает / отклоняет её;
- либо используется доверенный автоматический режим с журналом и возможностью отката.

## 7. LocalStorage и ключи

### 7.1. Принцип
LocalStorage может содержать только owner-привязанные рабочие ключи.

Корректный вид ключей:
- `abonents_{owner}`
- `payments_{owner}`
- `tariffs_{owner}`
- `ref_rates_{owner}`
- другие owner-bound ключи системы

### 7.2. Запрет
Запрещено:
- хранить общие тарифы без owner-суффикса;
- хранить ставки без owner-суффикса;
- использовать абонента как основной уровень хранения тарифов;
- смешивать данные разных owner в одном и том же ключе.

### 8.1. Backend
Backend обязан:
- вычислять owner только из сессии;

- запрещать user-ролям менять тарифы и ставки;

### 8.2. Frontend

- показывать read-only представление для user;
- не считать скрытие кнопки единственной защитой;
- работать через серверные проверки прав.

## 11. Persist-архитектура (новый этап)

### 11.1. Общий принцип

Система переходит от массовой синхронизации (`uploadNow`) к точечному сохранению (`persist`).

### 11.2. Разделение ответственности

- справочники (tariffs, далее ref_rates):
  → сохраняются через `JKHPersist` (по ключу)

- расчётные данные (abonents, accruals):
  → сохраняются через `uploadNow`

### 11.3. Причина

Разделение:
- уменьшает гонки данных
- устраняет рассинхрон между устройствами
- делает систему предсказуемой

### 11.4. Текущий статус

- tariffs → уже на persist
- accruals → остаются на uploadNow

### 11.5. Ограничение

Полный отказ от uploadNow запрещён до переноса:
- abonents
- payments
- accruals

### 11.6. Запрещено

- смешивать persist и uploadNow для одной сущности
- сохранять тарифы через uploadNow

## 0. Назначение

Этот документ фиксирует изменения, внесённые после стабилизации цепочки:

`server-first load → payments_<ЛС> ledger → autoaccrual → index.html → spravka_sud → upload whitelist`.

Цель документа: не допустить повторного появления уже найденных ошибок:
- пустой индекс после автозагрузки;
- пустая судебная справка при существующем ledger;
- `changed:true` без сохранённого результата;
- падение UI из-за `Data.flushDbToServer()`;
- отправка legacy/admin/global ключей на `/api/store` и 403.

## 1. Источник истины данных

### 1.1. Backend — главный источник

Серверная БД является главным источником данных.  
Frontend и `localStorage` используются как runtime-cache и транспортный слой.

### 1.2. UI не должен зависеть от успешности upload

Страницы обязаны строиться из локально доступного owner-scoped кэша после server-first загрузки.

Запрещено:
```js
await Data.flushDbToServer();
// и дальше строить UI только если upload успешен
```

Правильно:
```js
try {
  await Data.flushDbToServer();
} catch (e) {
  console.warn('[module] flush failed but continue', e);
}

// UI строится всё равно
rebuildOrRender();
```

Обязательное правило: ошибка sync/upload не должна оставлять `index.html`, `spravka_sud.js` или карточку абонента пустыми, если данные уже есть локально.

---

## 2. payments_<ЛС> — канонический ledger

### 2.1. Назначение

`payments_<ЛС>` — помесячный ledger абонента. Это не журнал событий, а рабочая таблица начислений/оплат.

В одном месяце допустимы:
- строка начисления;
- одна или несколько строк оплат;
- строки с уточнением оплаты за период.

### 2.2. Минимальная структура строки

Строка ledger должна поддерживать поля:
```js
{
  year: 2025,
  month: 1,
  accrued: 538.00,
  paid: 0,
  paid_date: '',
  id: '...'
}
```

### 2.3. Проверка пригодности ledger

Ledger считается пригодным для пропуска autoaccrual только если есть хотя бы одна строка с:

```js
Number(row.accrued) > 0
```

Важно:
- `paid > 0` без `accrued > 0` НЕ считается полноценным ledger;
- импорт платежей может создать оплаты без начислений;
- в этом случае autoaccrual обязан восстановить начисления.

## 3. Autoaccrual

### 3.1. Назначение

`autoaccrual_engine.js` создаёт/восстанавливает начисления в `payments_<ЛС>`.

### 3.2. Обязательное owner-scoped сохранение

`JKHAutoAccrual.recalcForAbonent(ls)` обязан читать и писать ledger в одном owner-scope:

```js
const ownerId = JKHStore.getOwnerId();
JKHStore.setRaw('payments_' + ls, JSON.stringify(rows), ownerId);
const check = JKHStore.getRaw('payments_' + ls, ownerId);
```

Запрещено:
- писать `payments_<ЛС>` без ownerId;
- читать из одного owner, а писать в другой;
- возвращать `changed:true`, если после расчёта `rows.length === 0`.

### 3.3. Обязательные диагностические логи

После записи:
```js
console.log('[autoaccrual][save]', { id: ls, rowsCount: rows.length, owner: ownerId });
```

После проверки:
```js
console.log('[autoaccrual][after-save]', { id: ls, exists: !!check, len: parsed.length });
```

## 4. index.html

### 4.1. Роль главной страницы

`index.html` не является главным расчётчиком.  
Главная страница — умный читатель ledger.

Правильный порядок:
1. дождаться `JKH_UI_STATE.data.status === ready|empty`;
2. проверить `payments_<ЛС>`;
3. если ledger пригоден — `skip existing`;
4. если начисления отсутствуют — точечно вызвать `recalcForAbonent(id)`;
5. после пересчёта всегда выполнить `rebuildIndexRows(); render();`.

### 4.2. Запрещено

Запрещено на главной:
- делать массовый `recalcAll()` без проверки ledger;
- запускать бесконечный пересчёт при каждом `JKH_UI_STATE_CHANGED`;
- блокировать render из-за ошибки upload;
- считать ledger пригодным только по `paid > 0`.

### 4.3. Обязательная защита от повторов

Должны быть флаги:
- `indexAutoAccrualInFlight`;
- `indexAutoAccrualDoneForOwner`.

Owner учитывается через:
```js
JKHStore.getOwnerId()
```

## 5. spravka_sud.js

### 5.1. Роль судебной справки

Справка суда — производная от ledger. Она не должна менять юридическую логику карточки.

### 5.2. Поведение перед построением

Перед чтением таблицы справка обязана:
1. прочитать `payments_<ЛС>`;
2. проверить наличие `accrued > 0`;
3. если начислений нет — вызвать `JKHAutoAccrual.recalcForAbonent(ctx.abonentId)`;
4. если был пересчёт — попытаться `Data.flushDbToServer()` через `try/catch`;
5. независимо от результата flush повторно прочитать `payments_<ЛС>`;
6. построить справку.

### 5.3. Обязательное правило

`SERVER_UPLOAD_FAILED` не имеет права останавливать построение справки, если локальный ledger уже создан.

Обязательный лог после перечитывания:
```js
console.log('[spravka_sud][ledger-after-recalc] id=' + ctx.abonentId + ' len=' + allRows.length);
```

## 6. Upload whitelist

### 6.1. Главный принцип

Обычный upload работает только по whitelist.

Запрещён принцип:
> отправить всё, кроме blacklist.

Разрешён принцип:
> отправить только явно разрешённые owner-ключи.

Функция-граница:
```js
_isUploadAllowedKey(baseKey, ownerId)
```

Любой ключ вне whitelist:
- не отправляется;
- логируется;
- не считается ошибкой UI.

Лог:
```js
console.warn('[JKH sync][skip-upload-not-allowed]', key);
```

## 9. Legacy keys

Legacy-ключи допустимы только как read-only/migration fallback.

Примеры:
- `tariffs_dynamic_v1`
- `tariffs_content_repair_v1`
- `tariffs_content_repair_v1_backup`

Если такой ключ найден в localStorage/cache:
- его можно прочитать для миграции;
- его нельзя отправлять на сервер;
- его нельзя использовать как новый источник записи.

## 10. Запрет молчаливого расчёта при отсутствии ставок

Если дата начала расчёта/регистрации/долга абонента раньше первой доступной ставки рефинансирования:
- система обязана показать понятное информационное предупреждение;
- расчёт пени / судебной справки должен быть остановлен до исправления данных;
- запрещено молча применять первую найденную ставку задним числом;
- запрещено молча считать пеню как 0.

Это правило распространяется на:
- `CalcEngine`;
- `spravka_sud`;
- карточку абонента;
- отчёты.

## 11. Обязательные проверки после изменений

### 11.1. Browser

После `Ctrl+F5` на `index.html`:
- нет `SyntaxError`;
- нет `POST /api/store 403`;
- таблица заполнена;
- при существующем ledger видно `skip existing payments_...`;
- при отсутствии ledger создаётся autoaccrual и затем выполняется rebuild.

### 11.2. Судебная справка

После открытия `spravka_sud.html?abonent=<ЛС>`:
- справка строится;

## 15. UID-only Payments + Premise Merge Canon v1.9.0 — 2026-05-03

### 15.1. Главный канон оплат

Лицевой счёт (`ЛС`, `abonentId`, бухгалтерский номер) больше не является техническим ключом оплат.
Он может повторяться у разных исторических и новых абонентов.

Единственный технический ключ оплат — `uid` абонента.

Канонический ключ ledger:

```text
payments_<uid>
```

Запрещено для новых/актуальных абонентов:

```text
payments_<ЛС>
payments_<abonentId>
payments_<accountNumber>
payments_<ls>
```

Все чтение/запись оплат, начислений, autoaccrual, import, карточка абонента, index и calc engine обязаны получать ключ только через канонический резолвер:

```js
window.getPaymentsKeyForAbonent(abonentId)
```

Если ключ не получен — операция чтения/записи ledger блокируется. Нельзя молча падать в `payments_<ЛС>`.

### 15.2. UID обязателен

У каждого абонента должен быть `uid`.

При создании абонента:
- `uid` генерируется всегда;
- нельзя сохранять нового абонента без `uid`;
- повторение ЛС допустимо, повторение UID запрещено.

При нормализации базы (`normalizeDb`) допускается мягкая миграция старых записей без UID:
- абоненту присваивается новый UID;
- старые `payments_<ЛС>` автоматически не переносятся;
- перенос legacy ledger возможен только отдельной осознанной миграцией.

### 15.3. Старые ключи оплат

Старые ключи вида `payments_<ЛС>` могут физически оставаться в localStorage/server storage, но новая логика не имеет права читать их для абонента с UID.

Диагностика legacy-ключей допускается через отдельную функцию, например:

```js
window.JKHDebugListLegacyPaymentKeys()
```

Автоматически удалять старые `payments_<ЛС>` запрещено без отдельного подтверждения/миграционного сценария.

### 15.4. Server-first init для оплаты

`DOMContentLoaded` не имеет права запускать чтение оплат.

Таблица оплат стартует только после готовности данных:

```text
JKH_UI_STATE.data.status === "ready"
```

Правильный порядок:

```text
DATA READY
→ init карточки абонента
→ определение abonent.uid
→ getPaymentsKeyForAbonent(abonentId)
→ чтение payments_<uid>
→ autoaccrual / render
```

Если Data или payment key не готовы:
- не читать storage;
- не создавать пустой ledger по ЛС;
- не писать в `payments_<ЛС>`;
- логировать blocked/read skipped.

### 15.5. Канон объединения квартир

Объединение квартир — отдельная бизнес-операция преобразования объекта недвижимости.

Исходные квартиры выбираются только из списка активных квартир.
Ручной ввод исходных regnum через запятую запрещён.

При объединении минимум двух активных квартир:

1. Старые квартиры:
   - получают `status = "merged"`;
   - получают `closedAt = date объединения - 1 день`;
   - получают `closedReason = "Объединение квартир"`;
   - получают `mergedIntoRegnum = <новый regnum>`;
   - остаются в базе как история.

2. Старые активные links:
   - закрываются `dateTo = closedAt`;
   - старым абонентам ставится `calcEndDate = closedAt`;
   - старые долги, начисления и платежи остаются на старых UID/ledger.

3. Новая квартира:
   - создаётся автоматически как новый объект;
   - получает новый внутренний `regnum` автоматически (`TEMP-YYYYMMDD-XXXX`), если UI не передал допустимый regnum;
   - получает `createdAt = date объединения`;
   - получает `status = "active"`;
   - получает `createdFromMergeRegnums = [старые regnum]`;
   - получает `mergedAt = date объединения`;
   - официальный номер (`officialRegnum`) допускается, но должен быть уникален.

4. Новый абонент:
   - создаётся как новый учётный объект;
   - получает новый ЛС формата `<nextNumeric>-<flat>`;
   - получает новый UID;
   - получает `calcStartDate = date объединения`;
   - получает `calcEndDate = ""`;
   - получает новую активную связь с новой квартирой;
   - копирует от выбранного ответственного только персональные поля: ФИО, телефон, доля, комнаты;
   - не наследует старые платежи и долги.

5. Новый link:

```js
{
  abonentId: newLs,
  regnum: newRegnum,
  dateFrom: mergeDate,
  dateTo: ""
}
```

6. Событие преобразования записывается в `premiseEvents`.
Полную историю преобразований хранить в `premiseEvents`, а в `premises` — только текущий статус и ссылки.

### 15.6. Запрет создания активного абонента на закрытой квартире

Если квартира имеет:

```text
status !== "active"
```

или заполнен:

```text
closedAt
```

то создание нового активного абонента запрещено.

Сообщение:

```text
Квартира закрыта/объединена. Создание нового активного абонента запрещено.
```

Кнопка `абонент+` должна быть disabled/скрыта.
В карточке закрытой/merged квартиры запрещены действия:
- сменить ответственного;
- преобразовать квартиру;
- создать новую активную связь.

### 15.7. UI-видимость исторических объектов

Закрытые/объединённые квартиры и абоненты не удаляются из интерфейса полностью.
Они должны быть видимы как история, но визуально помечены:

```text
объединена
расчёт остановлен
закрыта
```

На главной странице и в списке квартир исторические строки должны быть отделены визуально и не мешать активным объектам.
Активные квартиры выводятся выше merged/closed/archived.

### 15.8. Обязательные регресс-тесты

1. Повторный ЛС:
   - оставить старый `payments_1001`;
   - удалить абонента 1001;
   - создать нового абонента с ЛС 1001;
   - проверить, что новый абонент читает только `payments_<uid>`;
   - старые оплаты не появляются.

2. Объединение квартир:
   - объединить две активные квартиры;
   - старые квартиры стали `merged`;
   - старые абоненты получили `calcEndDate`;
   - новая квартира получила новый regnum;
   - новый абонент получил новый ЛС и UID;
   - новый ledger пустой/создаётся заново по UID.

3. Запрет на closed/merged:
   - попытаться создать абонента на merged-квартире;
   - создание запрещено понятным сообщением.

4. Логи:
   - не должно быть `payments_1001` для нового абонента с UID;
   - должны быть `payments_uid...`;
   - `index`, `payment_table`, `autoaccrual`, `calc_engine`, `import_xls` используют UID-key.
