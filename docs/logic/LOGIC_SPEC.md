## 0. Назначение документа

Этот документ фиксирует обязательную архитектуру и права доступа для:
- тарифов;
- ставок рефинансирования;
- изоляции данных по owner;
- синхронизации данных между устройствами;
- будущего автoобновления ставок с сервера.

Если старые документы противоречат этому файлу, приоритет у этого файла и у `docs/critical/CRITICAL_CHANGELOG.md`.

## 1. Ownership и изоляция данных (CRITICAL)

### 1.1. Общее правило
Все рабочие данные системы принадлежат конкретному `owner` (user_id).

К сущностям owner-пространства относятся:
- abonents
- payments
- accruals
- tariffs
- refinance_rates
- exclusion_periods
- premises / links
- notes / calc periods / report periods / related service data

### 1.2. Источник owner
`owner` определяется **только сервером** из серверной сессии.

Запрещено:
- передавать owner с клиента как источник истины;
- доверять owner из localStorage, query string, body, hidden fields;
- выполнять save/load/delete/sync без серверного owner.

### 1.3. Последствие
Каждый пользователь работает только со своей базой.  
Данные разных пользователей полностью изолированы.

## 2. Источник истины и синхронизация

### 2.1. Источник истины
- **Backend / серверная БД** — источник истины.
- **Frontend / localStorage** — рабочий кэш, офлайн-копия и транспортный слой.

### 2.2. Синхронизация
После логина и при явной загрузке с сервера клиент должен иметь возможность получить **полный набор данных owner**.

Минимальное требование:
- сервер поддерживает выгрузку полного набора ключей owner (`store_dump` или эквивалент);
- клиент умеет восстановить локальную рабочую копию из серверного набора.

### 2.3. Критический дефект
Если тарифы или ставки не синхронизируются между двумя устройствами одного owner, это считается **критической ошибкой синхронизации**.

## 3. Тарифы

### 3.1. Модель
Тарифы являются сущностью уровня `owner`.

Правильно:
- у каждого пользователя своя независимая база тарифов;
- один набор тарифов действует для всех абонентов этого пользователя;
- тарифы не принадлежат отдельному абоненту.

Неправильно:
- хранить тарифы на уровне конкретного абонента;
- дублировать один и тот же тариф по каждому абоненту;
- менять логику так, чтобы тариф был частью карточки абонента как первичный источник.

### 3.2. Структура
Тариф хранится как историческая запись:
- tariff_content
- tariff_repair
- start_date

Правило:
- последний тариф действует до появления нового;
- тариф вводится с начала месяца;
- один месяц имеет одну актуальную тарифную запись на owner-уровне.

### 3.3. Права доступа
- **Администратор**: создание / редактирование / удаление тарифов.
- **Пользователь**: только просмотр (`read-only`).

### 3.4. Применение
Начисление абонента считается по формуле:

`начисление = тарифы owner × площадь абонента`

Абонент хранит:
- площадь;
- адресные и идентификационные данные;
- свою финансовую историю.

Абонент **не хранит собственный тарифный справочник**.

## 4. Ставка рефинансирования

### 4.1. Модель
Ставки рефинансирования являются сущностью уровня `owner`.

Они:
- общие для всех абонентов данного пользователя;
- применяются в расчёте пени ко всем его абонентам;
- хранятся как история по датам.

### 4.2. Жёсткое правило прав доступа
**Изменять ставки рефинансирования может только администратор.**

Права:
- **Администратор**: полный CRUD.
- **Пользователь**: только просмотр (`read-only`), без права изменения.

Любая попытка изменения ставки от роли `user` должна завершаться отказом доступа.

### 4.3. Пересчёт
После изменения ставки:
- система должна инициировать корректный пересчёт пени;
- перерасчёт должен быть воспроизводимым и аудируемым;
- история прежних ставок обязана сохраняться.

### 4.4. Логирование
Каждое изменение ставки должно логироваться минимум с полями:
- user_id / actor_id
- старая ставка
- новая ставка
- дата изменения
- тип изменения
- источник изменения (manual / import / auto-update)

## 5. Сообщение об ошибке ставки

### 5.1. Назначение
Пользователь не меняет ставку напрямую, но может отправить сигнал:
**«ошибка в ставке рефинансирования»**.

### 5.2. Минимальная модель
Сообщение должно содержать:
- type = `refinance_rate_issue`
- text
- created_at
- user_id / owner
- optional related_date

### 5.3. Смысл
Разделение обязанностей:
- изменение справочника ставок — только администратор;
- сообщение о возможной ошибке — пользователь.

## 6. Будущее автообновление ставок из интернета

### 6.1. Разрешённое направление развития
В дальнейшем допускается автоматическое обновление ставок из внешнего источника:
- через API;
- через серверный парсер;
- через контролируемый AI-assisted механизм.

### 6.2. Ограничения
Такое обновление допускается **только на сервере** и только при соблюдении правил:
- сохраняется история всех значений;
- фиксируется источник данных;
- логируется время и результат обновления;
- есть защита от тихой подмены данных;
- расчёт остаётся воспроизводимым.

### 6.3. Что запрещено
Запрещено:
- менять ставки автоматически на клиенте;
- менять ставку без истории;
- менять ставку без логирования;
- подменять ставку постфактум без следа в аудите.

### 6.4. Предпочтительная модель
Предпочтительно:
- автообновление предлагает новую запись;
- администратор подтверждает / отклоняет её;
- либо используется доверенный автоматический режим с журналом и возможностью отката.

## 7. LocalStorage и ключи

### 7.1. Принцип
LocalStorage может содержать только owner-привязанные рабочие ключи.

Корректный вид ключей:
- `abonents_{owner}`
- `payments_{owner}`
- `tariffs_{owner}`
- `ref_rates_{owner}`
- другие owner-bound ключи системы

### 7.2. Запрет
Запрещено:
- хранить общие тарифы без owner-суффикса;
- хранить ставки без owner-суффикса;
- использовать абонента как основной уровень хранения тарифов;
- смешивать данные разных owner в одном и том же ключе.

## 8. Обязательные требования к API и UI

### 8.1. Backend
Backend обязан:
- вычислять owner только из сессии;
- отбрасывать попытки client-side spoofing owner;
- запрещать user-ролям менять тарифы и ставки;
- возвращать корректные коды ошибок доступа.

### 8.2. Frontend
Frontend обязан:
- скрывать или дизейблить кнопки редактирования тарифов и ставок для не-админа;
- показывать read-only представление для user;
- не считать скрытие кнопки единственной защитой;
- работать через серверные проверки прав.

## 11. Persist-архитектура (новый этап)

### 11.1. Общий принцип

Система переходит от массовой синхронизации (`uploadNow`) к точечному сохранению (`persist`).

### 11.2. Разделение ответственности

- справочники (tariffs, далее ref_rates):
  → сохраняются через `JKHPersist` (по ключу)

- расчётные данные (abonents, accruals):
  → сохраняются через `uploadNow`

### 11.3. Причина

Разделение:
- уменьшает гонки данных
- устраняет рассинхрон между устройствами
- делает систему предсказуемой

### 11.4. Текущий статус

- tariffs → уже на persist
- accruals → остаются на uploadNow

### 11.5. Ограничение

Полный отказ от uploadNow запрещён до переноса:
- abonents
- payments
- accruals

### 11.6. Запрещено

- смешивать persist и uploadNow для одной сущности
- сохранять тарифы через uploadNow
