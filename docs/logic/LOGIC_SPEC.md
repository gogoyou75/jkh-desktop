## 0. Назначение документа

Этот документ фиксирует обязательную архитектуру и права доступа для:
- owner-изоляции;
- тарифов;
- ставок рефинансирования;
- синхронизации данных между устройствами;
- server-first импорта платежей;
- fingerprint-lock и антидубля.

Если старые документы противоречат этому файлу, приоритет у этого файла, у `docs/critical/CRITICAL_CHANGELOG.md` и у `docs/IMPORT_CANON_v2.0.md`.

## 1. Ownership и изоляция данных (CRITICAL)

### 1.1. Общее правило
Все рабочие данные системы принадлежат конкретному `owner` (user_id).

К owner-пространству относятся:
- abonents
- payments
- accruals
- tariffs
- refinance_rates
- exclusion_periods
- import batches / import rows / fingerprint locks
- premises / links
- notes / calc periods / report periods / related service data

### 1.2. Источник owner
`owner` определяется только сервером из серверной сессии.

Запрещено:
- доверять owner из frontend;
- выполнять load/save/delete/sync/import/apply без серверного owner.

### 1.3. Последствие
Каждый пользователь работает только со своей базой.
Данные разных пользователей полностью изолированы.

---

## 2. Источник истины и синхронизация

### 2.1. Источник истины
- Backend / серверная БД — источник истины.
- Frontend / localStorage — кэш, офлайн-копия и транспортный слой.

### 2.2. Синхронизация
После логина и при явной загрузке с сервера клиент должен иметь возможность получить полный набор owner-данных.

### 2.3. Критический дефект
Если данные одного owner не синхронизируются между двумя его устройствами, это считается критической ошибкой.

---

## 3. Тарифы

### 3.1. Модель
Тарифы являются сущностью уровня owner.

### 3.2. Права
- Администратор: создание / редактирование / удаление тарифов.
- Пользователь: только просмотр.

### 3.3. Применение
Начисление = тарифы owner × площадь абонента.

---

## 4. Ставка рефинансирования

### 4.1. Модель
Ставки рефинансирования являются сущностью уровня owner.

### 4.2. Права
Изменять ставки рефинансирования может только администратор.

### 4.3. Логирование
Любое изменение ставки должно логироваться.

---

## 5. Импорт платежей (новый критический канон)

### 5.1. Общая модель
Импорт платежей — server-first подсистема.
Frontend не проводит платежи самостоятельно, а только:
- загружает файл;
- показывает preview;
- запускает server-side parse / validate / apply.

### 5.2. Batch-модель
Импорт платежей должен опираться на:
- `import_batch`
- `import_batch_rows`

### 5.3. Допуск к учёту платежа
**Платежи могут учитываться только если есть UID.**

Без UID:
- строка не проводится;
- fallback по ЛС/Фамилии для платежного apply запрещён.

### 5.4. Обязательные поля apply
Для проведения платежа обязательны:
- `account_uid`
- `account_number` (ЛС)

### 5.5. Fingerprint-lock
Антидубль реализуется через server-side fingerprint-lock:
- `import_applied_fingerprints`
- уникальность `(owner_id, import_type, fingerprint)`

### 5.6. Состав fingerprint
Fingerprint строится из:
- owner_id
- account_uid
- account_number
- paid_date
- amount
- source_index
- payment_period

### 5.7. Apply
Apply выполняется только на сервере и должен:
1. нормализовать данные;
2. резервировать fingerprint;
3. при успехе записывать платёж в текущий ledger;
4. при дубликате помечать строку duplicate;
5. возвращать summary.

### 5.8. Storage-совместимость
До полного рефакторинга storage сохраняется текущий канон:
- ledger key = `payments_<ЛС>`
- запись в `payments_<UID>` запрещена
- fingerprint и SQL могут использовать каноническую ISO-дату
- legacy KV/JSON ledger пока остаётся совместимым с текущим форматом клиента

### 5.9. Запрет на подмены
Запрещено:
- подменять отсутствующий UID значением ЛС;
- подменять отсутствующий ЛС значением UID;
- проводить платежи только по ЛС без UID.

---

## 6. LocalStorage и ключи

### 6.1. Принцип
LocalStorage может содержать только owner-bound рабочие ключи.

### 6.2. Импортный канон storage
Для текущего платежного ledger:
- storage key строится по ЛС;
- серверный import apply обязан соблюдать этот канон до отдельного решения о миграции storage.

---

## 7. Будущее развитие

### 7.1. Разрешено
В будущем допускается:
- полный перевод платежного ledger в отдельную SQL-таблицу;
- отказ от legacy KV/JSON storage;
- перенос всех duplicate-check и apply-механизмов в чистую SQL-модель.

### 7.2. Но сейчас
Пока это не реализовано, любые правки импорта обязаны:
- не ломать текущий `payments_<ЛС>` storage;
- усиливать надёжность поверх существующей архитектуры, а не разрушать её.

---

## 8. Критические дефекты

Критическими считаются:
- проведение платежей без UID;
- запись импортированных платежей в `payments_<UID>` вместо `payments_<ЛС>`;
- нарушение owner isolation в import/apply;
- отсутствие server-side fingerprint-lock;
- рассинхрон между импортом и текущим клиентским storage-каноном.
