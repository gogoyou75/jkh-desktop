## 15. UID-only Payments + Premise Merge Canon v1.9.0 — 2026-05-03

### 15.1. Главный канон оплат

Лицевой счёт (`ЛС`, `abonentId`, бухгалтерский номер) больше не является техническим ключом оплат.
Он может повторяться у разных исторических и новых абонентов.

Единственный технический ключ оплат — `uid` абонента.

Канонический ключ ledger:

```text
payments_<uid>
```

Запрещено для новых/актуальных абонентов:

```text
payments_<ЛС>
payments_<abonentId>
payments_<accountNumber>
payments_<ls>
```

Все чтение/запись оплат, начислений, autoaccrual, import, карточка абонента, index и calc engine обязаны получать ключ только через канонический резолвер:

```js
window.getPaymentsKeyForAbonent(abonentId)
```

Если ключ не получен — операция чтения/записи ledger блокируется. Нельзя молча падать в `payments_<ЛС>`.

### 15.2. UID обязателен

У каждого абонента должен быть `uid`.

При создании абонента:
- `uid` генерируется всегда;
- нельзя сохранять нового абонента без `uid`;
- повторение ЛС допустимо, повторение UID запрещено.

При нормализации базы (`normalizeDb`) допускается мягкая миграция старых записей без UID:
- абоненту присваивается новый UID;
- старые `payments_<ЛС>` автоматически не переносятся;
- перенос legacy ledger возможен только отдельной осознанной миграцией.

### 15.3. Старые ключи оплат

Старые ключи вида `payments_<ЛС>` могут физически оставаться в localStorage/server storage, но новая логика не имеет права читать их для абонента с UID.

Диагностика legacy-ключей допускается через отдельную функцию, например:

```js
window.JKHDebugListLegacyPaymentKeys()
```

Автоматически удалять старые `payments_<ЛС>` запрещено без отдельного подтверждения/миграционного сценария.

### 15.4. Server-first init для оплаты

`DOMContentLoaded` не имеет права запускать чтение оплат.

Таблица оплат стартует только после готовности данных:

```text
JKH_UI_STATE.data.status === "ready"
```

Правильный порядок:

```text
DATA READY
→ init карточки абонента
→ определение abonent.uid
→ getPaymentsKeyForAbonent(abonentId)
→ чтение payments_<uid>
→ autoaccrual / render
```

Если Data или payment key не готовы:
- не читать storage;
- не создавать пустой ledger по ЛС;
- не писать в `payments_<ЛС>`;
- логировать blocked/read skipped.

### 15.5. Канон объединения квартир

Объединение квартир — отдельная бизнес-операция преобразования объекта недвижимости.

Исходные квартиры выбираются только из списка активных квартир.
Ручной ввод исходных regnum через запятую запрещён.

При объединении минимум двух активных квартир:

1. Старые квартиры:
   - получают `status = "merged"`;
   - получают `closedAt = date объединения - 1 день`;
   - получают `closedReason = "Объединение квартир"`;
   - получают `mergedIntoRegnum = <новый regnum>`;
   - остаются в базе как история.

2. Старые активные links:
   - закрываются `dateTo = closedAt`;
   - старым абонентам ставится `calcEndDate = closedAt`;
   - старые долги, начисления и платежи остаются на старых UID/ledger.

3. Новая квартира:
   - создаётся автоматически как новый объект;
   - получает новый внутренний `regnum` автоматически (`TEMP-YYYYMMDD-XXXX`), если UI не передал допустимый regnum;
   - получает `createdAt = date объединения`;
   - получает `status = "active"`;
   - получает `createdFromMergeRegnums = [старые regnum]`;
   - получает `mergedAt = date объединения`;
   - официальный номер (`officialRegnum`) допускается, но должен быть уникален.

4. Новый абонент:
   - создаётся как новый учётный объект;
   - получает новый ЛС формата `<nextNumeric>-<flat>`;
   - получает новый UID;
   - получает `calcStartDate = date объединения`;
   - получает `calcEndDate = ""`;
   - получает новую активную связь с новой квартирой;
   - копирует от выбранного ответственного только персональные поля: ФИО, телефон, доля, комнаты;
   - не наследует старые платежи и долги.

5. Новый link:

```js
{
  abonentId: newLs,
  regnum: newRegnum,
  dateFrom: mergeDate,
  dateTo: ""
}
```

6. Событие преобразования записывается в `premiseEvents`.
Полную историю преобразований хранить в `premiseEvents`, а в `premises` — только текущий статус и ссылки.

### 15.6. Запрет создания активного абонента на закрытой квартире

Если квартира имеет:

```text
status !== "active"
```

или заполнен:

```text
closedAt
```

то создание нового активного абонента запрещено.

Сообщение:

```text
Квартира закрыта/объединена. Создание нового активного абонента запрещено.
```

Кнопка `абонент+` должна быть disabled/скрыта.
В карточке закрытой/merged квартиры запрещены действия:
- сменить ответственного;
- преобразовать квартиру;
- создать новую активную связь.

### 15.7. UI-видимость исторических объектов

Закрытые/объединённые квартиры и абоненты не удаляются из интерфейса полностью.
Они должны быть видимы как история, но визуально помечены:

```text
объединена
расчёт остановлен
закрыта
```

На главной странице и в списке квартир исторические строки должны быть отделены визуально и не мешать активным объектам.
Активные квартиры выводятся выше merged/closed/archived.

### 15.8. Обязательные регресс-тесты

1. Повторный ЛС:
   - оставить старый `payments_1001`;
   - удалить абонента 1001;
   - создать нового абонента с ЛС 1001;
   - проверить, что новый абонент читает только `payments_<uid>`;
   - старые оплаты не появляются.

2. Объединение квартир:
   - объединить две активные квартиры;
   - старые квартиры стали `merged`;
   - старые абоненты получили `calcEndDate`;
   - новая квартира получила новый regnum;
   - новый абонент получил новый ЛС и UID;
   - новый ledger пустой/создаётся заново по UID.

3. Запрет на closed/merged:
   - попытаться создать абонента на merged-квартире;
   - создание запрещено понятным сообщением.

4. Логи:
   - не должно быть `payments_1001` для нового абонента с UID;
   - должны быть `payments_uid...`;
   - `index`, `payment_table`, `autoaccrual`, `calc_engine`, `import_xls` используют UID-key.

### 15.9. Запреты для будущих задач

Codex запрещено:
- возвращать `payments_<ЛС>` как fallback для абонента с UID;
- запускать чтение оплат на `DOMContentLoaded` до готовности Data;
- переносить платежи/долги при объединении квартир без отдельного ТЗ;
- перезаписывать старого абонента новой объединённой квартирой;
- создавать активного абонента на `merged/closed` квартире;
- хранить полную историю преобразований внутри `premises` вместо `premiseEvents`.
