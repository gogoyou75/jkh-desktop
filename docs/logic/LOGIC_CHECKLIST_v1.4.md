# ПАПАЖКХ — LOGIC_CHECKLIST v1.5

Назначение: контроль корректности логики после правок owner / тарифов / ставок / sync.

---

## CRITICAL минимум

1. Одно начисление на месяц.
2. Начисление readonly.
3. Формат оплаты 0.00, запятая нормализуется в точку.
4. Оплата за период влияет только на пеню.
5. Исключённые периоды отключают только пеню.
6. Мораторий меняет только применение ставок.
7. Нарастающий итог стабилен.
8. История не переносится при смене ответственного без специального механизма.
9. Новый абонент стартует с нуля.
10. owner определяется только сервером.
11. user не может изменять ставки рефинансирования.
12. user не может изменять тарифы.
13. тарифы принадлежат owner, а не абоненту.
14. ставки принадлежат owner и общие для всех его абонентов.
15. после server sync тарифы и ставки совпадают на двух устройствах одного owner.

---

## 1. Проверка ролей

### 1.1. Ставки
- зайти под admin → изменение ставки доступно;
- зайти под user → UI только read-only;
- попытка изменить ставку через API под user → отказ доступа.

### 1.2. Тарифы
- зайти под admin → изменение тарифа доступно;
- зайти под user → UI только read-only;
- попытка изменить тариф через API под user → отказ доступа.

---

## 2. Проверка owner-изоляции

- создать данные у owner A;
- войти под owner B;
- убедиться, что данные A не видны;
- убедиться, что owner не берётся из frontend.

---

## 3. Проверка синхронизации

- на устройстве 1 под owner изменить тариф под admin;
- выполнить сохранение на сервер;
- на устройстве 2 под тем же owner выполнить загрузку с сервера;
- новый тариф обязан появиться.

Повторить тот же тест для ставок.

---

## 4. Проверка сообщения об ошибке ставки

- под user открыть экран ставок;
- убедиться, что прямого редактирования нет;
- отправить сообщение об ошибке ставки;
- убедиться, что сообщение сохранилось / ушло в журнал.

---

## 5. Проверка будущей архитектуры автообновления

Подготовительный инвариант:
- автообновление ставок должно быть возможно только на backend;
- у каждой автоматически добавленной ставки должен быть источник и лог.

---

## 6. Ledger и расчёт

- `payments_<LS>` остаётся ledger;
- `use_period` не меняет основной долг;
- исключённый период отключает только пеню;
- расчёты до `calcStartDate` нового абонента дают ноль.

---

## 7. Критерий провала

Любой из сценариев ниже = критический провал:
- user изменил ставку;
- user изменил тариф;
- owner подменился с клиента;
- на двух устройствах одного owner разные ставки или тарифы после sync.
